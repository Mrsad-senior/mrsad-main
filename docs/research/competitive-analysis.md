# Competitive Analysis: Runtime Guardrails, AI Firewalls and MCP Gateways (as of October 2026)

*Mirsad (مرصاد) senior project, IS499, Prince Sultan University, 2026-2027. Research track: competitive analysis. All web sources were accessed on 11 October 2026.*

## 1. Introduction

This document compares Mirsad, a runtime firewall that sits between LLM agents and their tools, with the commercial products, open-source projects and research prototypes that a reviewer is most likely to bring up. We looked at nine product families in detail: Lakera Guard (now Check Point AI Guardrails), NVIDIA NeMo Guardrails, Meta LlamaFirewall with Prompt Guard 2, Microsoft Azure AI Content Safety Prompt Shields (with the Foundry guardrails around it), AWS Bedrock Guardrails (and the newer AgentCore Policy), Google Cloud Model Armor, Cloudflare AI Security for Apps (formerly Firewall for AI) and AI Gateway, Protect AI LLM Guard, and Invariant Labs Guardrails/MCP-scan (now part of Snyk). We also covered MCP gateways (Docker MCP Gateway, agentgateway, IBM ContextForge) and the CaMeL research prototype. Each product is assessed on eight dimensions taken from Mirsad's design: deployment point (model I/O or tool layer), per-tool and per-parameter policy, taint/data-flow tracking, Arabic injection detection, human approval, tamper-evident audit, licensing, and pricing model.

**Method and caveats.** Every claim comes from the vendor's own documentation, an official repository, a press release or a peer-reviewed or arXiv paper. "Not documented" means we found nothing in the pages we reviewed. It does not mean the vendor lacks the capability. We did not benchmark any product, so detection quality figures are vendor claims. This market changes month to month: three of the vendors were acquired during 2025, LLM Guard has been archived, and AWS made its agent-policy product generally available in 2026 after a December 2025 preview. The comparison should be checked again before the final report. References [65]-[67] were added during fact-checking and are listed under the product they support, so they appear out of numeric order. Mirsad's column shows its *design targets*, which the team still has to implement and evaluate. It does not show demonstrated capabilities.

### 2.1 Lakera Guard (now Check Point AI Guardrails)

**Sources**
- [1] Check Point Software Technologies, "Getting started with AI Guardrails," *Check Point AI Security documentation (docs.lakera.ai)*. Accessed: Oct. 11, 2026. [Online]. Available: https://docs.lakera.ai/docs/quickstart. Describes the Guard API, which the application calls for each LLM interaction, and the detection categories.
- [2] Check Point Software Technologies, "Prompt Defense," *Check Point AI Security documentation*. Accessed: Oct. 11, 2026. [Online]. Available: https://docs.lakera.ai/docs/prompt-defense. Covers prompt-attack coverage, including screening of tool responses and tool descriptions, and the 100+ supported languages (Arabic is listed).
- [3] Check Point Software Technologies, "Policies," *Check Point AI Security documentation*. Accessed: Oct. 11, 2026. [Online]. Available: https://docs.lakera.ai/docs/policies. Covers policy categories, including Agent Behavior Defense and blocking calls to tools outside an allow list, plus sensitivity levels L1-L4 and Detect/Enforce modes.
- [4] Check Point Software Technologies, "AI Agent Security overview," *Check Point AI Security documentation*. Accessed: Oct. 11, 2026. [Online]. Available: https://docs.lakera.ai/docs/agent-security. Describes agent posture and runtime guardrails and labels the feature an early-access release.
- [5] Check Point Software Technologies, "AI Guardrails dashboard," *Check Point AI Security documentation*. Accessed: Oct. 11, 2026. [Online]. Available: https://docs.lakera.ai/docs/platform. Lists Community vs. Enterprise limits, prompt logging defaults, S3/SIEM export and the note that the dashboard is not available to self-hosting customers.
- [6] Check Point Software Technologies, "Check Point acquires Lakera to deliver end-to-end AI security for enterprises," press release, Sep. 16, 2025. Accessed: Oct. 11, 2026. [Online]. Available: https://www.checkpoint.com/press-releases/check-point-acquires-lakera-to-deliver-end-to-end-ai-security-for-enterprises/
- [67] Check Point Software Technologies, "Check Point Software reports 2025 third quarter financial results," press release, Oct. 28, 2025. Accessed: Oct. 11, 2026. [Online]. Available: https://www.checkpoint.com/press-releases/check-point-software-reports-2025-third-quarter-financial-results/. States that the Lakera acquisition closed on October 22, 2025.

**Summary.** Lakera Guard is a hosted screening API. The application sends it user input, model output and, for agents, tool calls, tool responses and tool descriptions. The response says whether the content was flagged for prompt attacks, data leakage, content violations or unknown links [1], [2], [4]. Defenses are grouped into policies attached to projects. The documented policy examples include an Agent Behavior Defense category and blocking tools outside an allow list [3]. Prompt-attack screening is documented for more than 100 languages, and Arabic is named explicitly [2]. Check Point announced the Lakera acquisition in September 2025 [6] and closed it on 22 October 2025 [67], and the documentation is now branded as Check Point AI Guardrails.

**Strengths.** Lakera is one of only two commercial detectors in this sample that name Arabic for prompt-attack screening; the other is AWS Bedrock Guardrails in its Standard tier [24]. Its documentation explicitly covers indirect injection through tool responses and poisoned tool descriptions [2]. It offers a free Community tier limited to 10k screening requests per month, and Enterprise adds SIEM export and data-retention controls [5].
**Limitations.** Lakera is a classifier and policy API, so the application still decides what to do with a flag. The documentation describes no per-parameter rules, no taint tracking across calls and no human-approval workflow. The agent-security features are early access [4]. Prompts are logged by default to Check Point's SaaS unless the customer turns this off [5], which matters for data-sovereignty-sensitive users in Saudi Arabia. The docs do not describe tamper-evident logs.
**Relevance to Mirsad.** Lakera is the strongest benchmark for Mirsad's Arabic/English detector. Mirsad should not claim to be the only Arabic-capable injection detector. A fair claim is that Mirsad *combines* an Arabic-aware detector with deterministic tool-layer enforcement and approval. Mirsad's detector could also be evaluated against Lakera's free tier as a baseline.

### 2.2 NVIDIA NeMo Guardrails

**Sources**
- [7] NVIDIA, "Overview," *NVIDIA NeMo Guardrails Library Developer Guide*. Accessed: Oct. 11, 2026. [Online]. Available: https://docs.nvidia.com/nemo/guardrails/about-nemo-guardrails-library/overview. Describes the library and microservice deployment, the rail types and inspection of tool calls.
- [8] NVIDIA, "Guardrail types," *NVIDIA NeMo Guardrails Library Developer Guide*. Accessed: Oct. 11, 2026. [Online]. Available: https://docs.nvidia.com/nemo/guardrails/latest/about-nemo-guardrails-library/rail-types. Defines input, retrieval, dialog, execution and output rails. Execution rails validate tool calls, their arguments and their results.
- [9] NVIDIA, "Tools integration with the NeMo Guardrails library," *NVIDIA NeMo Guardrails Library Developer Guide*. Accessed: Oct. 11, 2026. [Online]. Available: https://docs.nvidia.com/nemo/guardrails/latest/integration-with-third-party-libraries/tools-integration. States that tool messages bypass input rails and that tool results are trusted by default, and recommends output rails as the mitigation.
- [10] NVIDIA, "Content safety," *NVIDIA NeMo Guardrails Library Developer Guide*. Accessed: Oct. 11, 2026. [Online]. Available: https://docs.nvidia.com/nemo/guardrails/latest/configure-guardrails/guardrail-catalog/content-safety. Covers multilingual refusal messages (nine languages, Arabic included) and notes that language detection only selects the refusal language.
- [11] NVIDIA, "NeMo Guardrails," GitHub repository NVIDIA-NeMo/Guardrails (release v0.24.1, Sep. 16, 2026). Accessed: Oct. 11, 2026. [Online]. Available: https://github.com/NVIDIA-NeMo/Guardrails. Apache-2.0 licence, execution rails for custom actions, and built-in jailbreak/injection detection.
- [12] T. Rebedea, R. Dinu, M. N. Sreedhar, C. Parisien, and J. Cohen, "NeMo Guardrails: A toolkit for controllable and safe LLM applications with programmable rails," in *Proc. 2023 Conf. Empirical Methods in Natural Language Processing: System Demonstrations (EMNLP)*, Dec. 2023, pp. 431-445, doi: 10.18653/v1/2023.emnlp-demo.40.

**Summary.** NeMo Guardrails is an open-source Python toolkit and microservice. Developers write "rails" in YAML and Colang that run before and after LLM calls, over retrieved chunks, over dialog flow, and around custom actions and tools [7], [8], [12]. Execution rails are documented as validating tool calls, their arguments and their results [8]. The tools-integration guide, however, warns that tool messages skip input rails and that tool results are trusted by default [9]. Built-in protections include jailbreak and injection detection [11]. The documented multilingual feature only changes the language of the refusal message: Arabic is one of the nine refusal-message languages, while the languages covered by the jailbreak and injection detectors are not stated [10].

**Strengths.** NeMo is mature, actively released (v0.24.1, 16 September 2026), Apache-2.0 licensed [11] and highly programmable. Execution rails provide hooks at the tool layer, and Colang can express multi-turn dialog flows as policy [7], [12].
**Limitations.** Tool-layer enforcement is something the developer builds out of rails and custom Python. No declarative per-tool or per-parameter schema is documented. The documentation itself notes that tool outputs are trusted by default [9]. We found no taint tracking, human approval or tamper-evident logging in the docs reviewed. Arabic support for injection detection is not documented; Arabic appears only as a refusal-message language [10].
**Relevance to Mirsad.** NeMo is the closest open-source framework, and Mirsad could in principle be built as a set of NeMo execution rails. Mirsad differs by enforcing at a protocol proxy (MCP/function calling), outside the agent's code, and by treating tool outputs as untrusted by default. That default addresses exactly the gap NeMo's documentation acknowledges [9].

### 2.3 Meta LlamaFirewall and Llama Prompt Guard 2

**Sources**
- [13] Meta, "About LlamaFirewall," *LlamaFirewall documentation*. Accessed: Oct. 11, 2026. [Online]. Available: https://meta-llama.github.io/PurpleLlama/LlamaFirewall/docs/documentation/about-llamafirewall. Describes the layered scanners (PromptGuard 2, AlignmentCheck, CodeShield, regex) and the inspection of user input, agent reasoning, code and tool responses.
- [14] Meta, "LlamaFirewall," GitHub repository meta-llama/PurpleLlama (LlamaFirewall directory, MIT licence). Accessed: Oct. 11, 2026. [Online]. Available: https://github.com/meta-llama/PurpleLlama/tree/main/LlamaFirewall. Shows per-role scanner configuration and `scan_replay` over traces. AlignmentCheck needs an external LLM API (the README asks for a Together API key).
- [15] S. Chennabasappa *et al.*, "LlamaFirewall: An open source guardrail system for building secure AI agents," arXiv:2505.03574, May 2025. [Online]. Available: https://arxiv.org/abs/2505.03574
- [16] Meta, "Llama Prompt Guard 2 86M," model card, Hugging Face. Accessed: Oct. 11, 2026. [Online]. Available: https://huggingface.co/meta-llama/Llama-Prompt-Guard-2-86M. Covers the binary benign/malicious label, the 512-token window, the evaluation languages and the Llama 4 Community License.

**Summary.** LlamaFirewall is Meta's open-source guardrail framework for agents. It combines PromptGuard 2, a small BERT-style jailbreak and injection classifier; AlignmentCheck, an LLM-based auditor that reads the agent's reasoning for signs of goal hijacking; CodeShield for insecure generated code; and regex or custom scanners [13]-[15]. Scanners are configured per message role and can replay whole traces [14]. Prompt Guard 2 dropped Prompt Guard 1's separate "injection" label and now flags explicit attempts to override instructions [16]. Both Prompt Guard 2 models were evaluated on English and seven other languages (French, German, Hindi, Italian, Portuguese, Spanish and Thai), and Arabic is not among them. The 22M model is weaker on multilingual data because its base model has no multilingual pretraining [16].

**Strengths.** LlamaFirewall is free and open (MIT code) and designed for agents. The paper presents AlignmentCheck, which it labels experimental, as a chain-of-thought auditor aimed at indirect injection and goal misalignment [15]. Prompt Guard 2 is small: the model card reports about 92 ms (86M) and 19 ms (22M) per 512-token classification on an A100 GPU [16].
**Limitations.** The system is detection- and reasoning-audit-based, with no deterministic per-tool or per-parameter authorization, no taint tracking, no approval workflow and no audit store in the docs reviewed. The latest PyPI release is 1.0.3 (May 2025), although the LlamaFirewall source directory [14] still received maintenance commits in August 2026, so release activity should be checked. Prompt Guard 2 is gated, requires a "Built with Llama" notice [16], has a 512-token window, and has no documented Arabic evaluation. AlignmentCheck depends on an external LLM API, which adds cost and latency [14].
**Relevance to Mirsad.** Prompt Guard 2 is a natural multilingual baseline for Mirsad's detector. The absence of documented Arabic evaluation is a concrete gap Mirsad can measure. LlamaFirewall supports Mirsad's layered design, and Mirsad adds the deterministic enforcement layer that LlamaFirewall leaves to the developer.

### 2.4 Microsoft Azure AI Content Safety Prompt Shields (and Foundry guardrails)

**Sources**
- [17] Microsoft, "Prompt Shields in Azure AI Content Safety," *Microsoft Learn*, Aug. 28, 2026. Accessed: Oct. 11, 2026. [Online]. Available: https://learn.microsoft.com/en-us/azure/ai-services/content-safety/concepts/jailbreak-detection. Covers user-prompt and document attacks, the attack subtypes, Spotlighting (preview), and the API limit of a user prompt plus up to five documents.
- [18] Microsoft, "Guardrails and controls overview in Microsoft Foundry," *Microsoft Learn*, Jul. 31, 2026. Accessed: Oct. 11, 2026. [Online]. Available: https://learn.microsoft.com/en-us/azure/foundry/guardrails/guardrails-overview. Describes the four intervention points (user input, tool call, tool response, output). Tool points are agent-only and in preview. Agents support "annotate and block" only.
- [19] Microsoft, "Agentic Workflows: Task Adherence (preview)," *Microsoft Learn*, Apr. 2, 2026. Accessed: Oct. 11, 2026. [Online]. Available: https://learn.microsoft.com/en-us/azure/foundry/guardrails/task-adherence. An ML signal that flags tool calls misaligned with user intent, for blocking or human-in-the-loop escalation. Tested on English text.
- [20] Microsoft, "Region availability and service limits - Azure AI Content Safety," *Microsoft Learn*, Sep. 18, 2026. Accessed: Oct. 11, 2026. [Online]. Available: https://learn.microsoft.com/en-us/azure/ai-services/content-safety/region-availability. States that Prompt Shields was "tested with English only". Also gives the Prompt Shields API input limits (prompt up to 10K characters; up to five documents totalling 10K characters) and region tables.
- [21] Microsoft, "Connect agents to MCP server endpoints," *Microsoft Learn*, Aug. 26, 2026. Accessed: Oct. 11, 2026. [Online]. Available: https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/model-context-protocol. Covers `allowed_tools`, `require_approval` (default "always": a developer must provide approval for every call), and the `mcp_approval_request` items that the client application must answer. Advises logging approvals and tool calls for auditing.
- [22] Microsoft Azure, "Content Safety in Foundry Control Plane - pricing." Accessed: Oct. 11, 2026. [Online]. Available: https://azure.microsoft.com/en-us/pricing/details/content-safety/. Free tier of 5,000 text records per month. The Standard tier is billed per 1,000 text records (1 record = up to 1,000 characters).

**Summary.** Prompt Shields is a hosted classifier for two attack types: user-prompt attacks (jailbreaks) and document attacks (indirect injection hidden in emails, documents or web pages) [17]. In Microsoft Foundry it is one control inside a "guardrail"; document-attack scanning runs at the user-input and, for agents (preview), tool-response intervention points [17], [18]. Spotlighting (preview) base64-encodes documents so that the model treats them as lower-trust input. It is available only for models used through the Chat Completions API and not for agents [17], [18]. Foundry's agent platform separately offers per-MCP-tool allow lists and an approval gate (`require_approval`). Approval requests are returned to the calling application, so the approval user experience is the developer's to build [21]. Task Adherence (preview) flags tool calls that do not match the user's intent [19]. Microsoft states that Prompt Shields was tested with English only and may work in other languages with varying quality [20].

**Strengths.** Prompt Shields has the most explicit indirect-injection taxonomy of the cloud vendors. Inspection at the tool-response point is integrated into the agent runtime. The platform provides approval primitives and an intent-alignment signal [19], [21], and there is a free tier [22].
**Limitations.** Arabic was not tested [20], and Prompt Shields API inputs are capped at 10K characters for the prompt and 10K characters across up to five documents [20]. Tool-call and tool-response scanning are preview features that apply only to Foundry agents [18], and Task Adherence is also in preview [19]. Spotlighting marks provenance for the model; it does not track or enforce data flow. No per-parameter declarative policy and no tamper-evident audit are documented. The approval UX and the audit log are left to the developer [21].
**Relevance to Mirsad.** Azure confirms that tool-response inspection and approval gates are becoming standard features of the major platforms. Mirsad's differentiators are vendor neutrality (any MCP or OpenAI-style agent), Arabic evaluation, a ready-made mobile approval app, and taint-based sink rules rather than an ML intent signal.

Available: https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-log-file-validation-intro.html. - [34] Amazon Web Services, "Amazon Bedrock AgentCore pricing." Accessed: Oct. 11, 2026. [Online]. Available: https://aws.amazon.com/bedrock/agentcore/pricing/. Policy authorization costs $0.000025 per request, and natural-language policy authoring costs $0.13 per 1,000 input tokens.

**Summary.** AWS now ships two layers. *Bedrock Guardrails* is a model-I/O filter. Its prompt-attack category covers jailbreaks, injections and (in the Standard tier) prompt leakage, but with the InvokeModel APIs it requires developers to tag user input, and it explicitly does not evaluate tool results or tool definitions [23]. Its Standard tier lists Arabic as "optimized and supported" [24]. *AgentCore Policy* (preview 2 December 2025 [66], generally available 3 March 2026 [30]) is a tool-layer authorizer. Every MCP tool call through an AgentCore Gateway is checked against default-deny Cedar policies that can reference the caller's identity and the tool's input parameters [27], [28], [65]. Dogwood temporal policies add session-history conditions, for example "permit SellShares only if a matching ApproveSale response occurred in the last hour" [29]. Since June 2026, policies can also use Bedrock Guardrails signals to screen tool outputs and gateway inputs for prompt injection [31]. Bedrock Agents additionally offers a per-function `requireConfirmation` flag [26].

**Strengths.** This is the most complete commercial offering for Mirsad's problem. It offers deterministic, default-deny, per-tool and per-parameter policy outside the agent's code [27], [28], [65], session-aware rules [29], Arabic-capable injection classification [24], [31], CloudWatch decision logs [27], and optional CloudTrail data events [32] whose log files can be integrity-validated with chained signed digests [33]. Pricing is published [25], [34].
**Limitations.** Enforcement covers only traffic routed through an AgentCore Gateway [27]. Temporal policies additionally require the gateway and all its targets to be in the same AWS account and Region and are not offered in every Region [29], and the Guardrails-in-policy integration launched in only five Regions [31]. Temporal rate limits apply per session, and the caller supplies the session ID [29], [65]. No taint labelling of untrusted content is documented. Temporal rules correlate prior actions, but they do not track where a value originated. Approval is modelled as a prior *tool action* in policy. The documentation does not include an approval app for end users. CloudTrail integrity validation is opt-in, applies to log files rather than individual decisions, and redacts arguments [32], [33]. It is a proprietary managed service.
**Relevance to Mirsad.** AgentCore Policy is Mirsad's closest commercial analogue, and the project report should acknowledge this directly. Mirsad's case rests on four points: (i) it is self-hostable and cloud-neutral, which suits Saudi data-residency needs; (ii) its taint rules link untrusted-content provenance to external sinks; (iii) it provides an integrated mobile approval channel; and (iv) its hash-chained audit records every decision, not only API calls. Mirsad's policy language could borrow ideas from the default-deny and forbid-overrides-permit semantics that AgentCore enforces for Cedar policies [29], [65].

### 2.6 Google Cloud Model Armor (and Agent Gateway)

**Sources**
- [35] Google Cloud, "Model Armor overview," *Google Cloud documentation*, updated Oct. 9, 2026. Accessed: Oct. 11, 2026. [Online]. Available: https://docs.cloud.google.com/model-armor/overview. Covers the filters (responsible AI, prompt injection and jailbreak, Sensitive Data Protection, malicious URLs), single-turn stateless inspection, the tested languages and Cloud Logging.
- [36] Google Cloud, "Integrate Model Armor with Google and Google Cloud MCP servers," *Google Cloud documentation*, updated Oct. 9, 2026. Accessed: Oct. 11, 2026. [Online]. Available: https://docs.cloud.google.com/model-armor/model-armor-mcp-google-cloud-integration. Project-wide floor settings sanitize `tools/call` and `prompts/get` traffic only for supported Google MCP servers.
- [37] Google Cloud, "Agent Gateway overview," *Gemini Enterprise Agent Platform documentation*, updated Oct. 9, 2026. Accessed: Oct. 11, 2026. [Online]. Available: https://docs.cloud.google.com/gemini-enterprise-agent-platform/govern/gateways/agent-gateway-overview. Describes ingress and egress governance, MCP attribute parsing to restrict specific tools, and Model Armor scanning of tool responses.
- [38] Google Cloud, "Security Command Center pricing." Accessed: Oct. 11, 2026. [Online]. Available: https://cloud.google.com/security-command-center/pricing. Model Armor standalone is free up to 2 million tokens per month, then $0.10 per million tokens. SCC Premium and Enterprise subscriptions include up to 3 billion tokens per month.

**Summary.** Model Armor is a managed screening service for prompts and responses. It filters for responsible-AI harms, prompt injection and jailbreaks, sensitive data and malicious URLs, and it treats each request as an independent single-turn check with no conversation history [35]. It can be applied inline to Google's own MCP servers through project-level "floor settings" that sanitize tool calls and tool responses. The coverage excludes `tools/list`, `resources/*`, notifications and other MCP methods, and Google advises not enabling the injection filter unless the MCP traffic carries natural language [36]. Google's Agent Gateway adds identity-based egress control that blocks connections unless a policy grants access, can restrict access to specific MCP tools, and can optionally call Model Armor on tool payloads and agent responses [37]. The injection filter was tested on nine languages (Chinese, English, French, German, Italian, Japanese, Korean, Portuguese and Spanish), and Arabic is not among them [35].

**Strengths.** Pricing is published and has a free monthly allotment [38]. MCP integration for supported Google-hosted servers is switched on through project floor settings rather than application code [36]. Agent Gateway gives default-deny egress and tool-level authorization [37].
**Limitations.** The service is stateless, so it cannot track data flow [35]. Floor settings apply project-wide with no per-tool or per-parameter rules, and they reach only supported Google MCP servers [36]. Arabic is not among the tested languages [35]. No human approval and no tamper-evident log are documented [36], [37].
**Relevance to Mirsad.** Model Armor is another strong detector baseline, and its MCP integration shows that vendors are moving screening to the tool boundary. Mirsad can stand out through stateful taint tracking, per-parameter rules and Arabic evaluation, and by working with any MCP server.

### 2.7 Cloudflare AI Security for Apps (formerly Firewall for AI), AI Gateway, MCP server portals

**Sources**
- [39] Cloudflare, "AI Security for Apps," *Cloudflare WAF documentation*, updated Sep. 8, 2026. Accessed: Oct. 11, 2026. [Online]. - [40] Cloudflare, "Prompt injection detection," *Cloudflare WAF documentation*, updated Apr. 16, 2026. Accessed: Oct. 11, 2026. [Online]. **Relevance to Mirsad.** Cloudflare shows the "AI firewall at the edge" model, which is different from Mirsad's position at the agent-to-tool boundary. Network-edge filtering cannot see tool outputs that the agent fetches from internal systems, which is a useful argument for placing the firewall at the tool layer.

**Summary.** Invariant Labs, an ETH Zurich spin-off, built three tools. *Guardrails* is a rule language for agent traces. Its rules can match a tool call with argument patterns (for example, `send_email` to an address outside the company) and can chain calls with a flow operator (`get_inbox -> send_email`) [50]. *Gateway* is a proxy that enforces these rules on LLM and MCP traffic [51]. *MCP-scan* is a scanner for tool poisoning and "toxic flows" [53]. Snyk acquired Invariant in June 2025 [49]. MCP-scan now redirects to Snyk Agent Scan, which sends tool metadata to a Snyk API for analysis [53]. The hosted Explorer that Gateway reported to was shut down in January 2026, although Explorer can still be run locally [52]. **Strengths.** Invariant's rule language is the closest open-source analogue to Mirsad's declarative policy. It expresses per-tool, per-argument and sequence-based ("flow") rules in a readable, Python-inspired syntax, and it is Apache-2.0 licensed [50].
**Limitations.** The maintenance status is uncertain. The open-source repositories have had little recent activity (the main Guardrails repository's last commit, in January 2026, moved documentation; the previous one was in July 2025, and the Gateway's last commit was in November 2025) and the hosted backend is gone [50]-[52]. The flow operator matches the order of events in a trace; it does not track where a value came from. The language coverage of the detector, any approval workflow and tamper-evident audit are not documented. Snyk's governance product currently works at the server level, and Snyk itself says it does not stop destructive actions inside an approved server [54].
**Relevance to Mirsad.** Invariant is the most important prior art for Mirsad's policy design and should be cited as such. Mirsad can extend the idea from sequence-based flows to true taint labels on untrusted content, and add Arabic detection, approval and a durable audit store.

Available: https://agentgateway.dev/docs/kubernetes/latest/documentation/mcp/guardrails/about/. - [62] IBM, "ContextForge (mcp-context-forge)," GitHub repository (Apache-2.0). Accessed: Oct. 11, 2026. [Online]. Available: https://github.com/IBM/mcp-context-forge. README and plugin READMEs (`plugins/README.md`, `plugins/external/llmguard`, `plugins/external/opa`, `plugins/external/cedar`) describe `tool_pre_invoke`/`tool_post_invoke` hooks, an LLM Guard plugin with a `PromptInjection` filter on prompt hooks, an OPA plugin that evaluates Rego policies on tool arguments, and a Cedar RBAC plugin.

**Summary.** MCP gateways put a single proxy between agents and many MCP servers. Docker's gateway runs each server in a resource-limited container (1 CPU and 2 GB by default), lets the operator enable specific tools, blocks secret-shaped data in tool traffic by default, can block network access, logs calls by default, and supports custom interceptors [56]-[58]. agentgateway, a Linux Foundation (LF Projects) project, authorizes MCP calls with CEL expressions. The documentation's examples reference tool names and JWT claims, and disallowed tools are filtered out of list responses. Arguments cannot be used in `mcpAuthorization` rules, but a route-level `authorization` policy can read `mcp.tool.arguments` [59]. Content inspection is delegated to an external "ExtMCP" processor [60], [61]. IBM ContextForge federates MCP, A2A and REST/gRPC services with authentication, rate limiting and a plugin framework of 40+ plugins; optional plugins add LLM Guard-based prompt-injection filtering on MCP prompt hooks, OPA (Rego) policies that can inspect tool arguments, and Cedar-based RBAC [62]. None of the three documents taint tracking, human approval or tamper-evident logs, and only ContextForge documents (plugin-based) prompt-injection filtering.

**Strengths.** These gateways are open source and production-oriented. They provide strong infrastructure isolation (Docker), identity-aware, tool-level authorization (agentgateway), and extensible policy plugins (ContextForge), and they are vendor-neutral.
**Limitations.** Their built-in policies are mostly tool on/off or identity-based. Argument-level rules need agentgateway's route-level authorization policy [59], ContextForge's OPA plugin [62], or Docker's custom interceptors [56]. ContextForge's only documented injection filter wraps the archived, English-only LLM Guard model [45], [47], [62], and the other two gateways have no built-in detector.
**Relevance to Mirsad.** These are the most likely *deployment hosts* or competitors for Mirsad's proxy. agentgateway in particular already offers open-source, vendor-neutral per-tool and argument-aware authorization, so Mirsad must not claim per-parameter policy as unique. Mirsad could be built as a Docker interceptor, an agentgateway ExtMCP processor or a ContextForge plugin rather than as a stand-alone proxy. The report should present Mirsad as adding a security-semantics layer (taint, Arabic detection, approval, audit) on top of this plumbing.

### 2.11 CaMeL (research prototype)

**Sources**
- [63] E. Debenedetti *et al.*, "Defeating prompt injections by design," arXiv:2503.18813, Mar. 2025 (v2, Jun. 2025). [Online]. Available: https://arxiv.org/abs/2503.18813
- [64] Google Research, "camel-prompt-injection: Code for the paper 'Defeating Prompt Injections by Design'," GitHub repository (Apache-2.0). Accessed: Oct. 11, 2026. [Online]. Available: https://github.com/google-research/camel-prompt-injection

**Summary.** CaMeL rebuilds the agent itself. A privileged LLM turns the trusted user request into a program in a restricted Python subset. A quarantined LLM parses untrusted data but cannot call tools. A custom interpreter keeps a data-flow graph and attaches "capabilities" (provenance and allowed readers) to every value, then checks security policies before each tool call [63]. On AgentDojo it reports solving 77% of tasks with provable security, against 84% for an undefended agent [63]. The paper blocks policy violations during evaluation and says that real deployments would ask the user to confirm instead. It also discusses user fatigue and remaining side channels [63]. The code is a research artifact that Google says it will not support or maintain [64].

**Strengths.** CaMeL offers the strongest guarantees in the sample: true data-flow/taint tracking with capability-based sink policies, and it does not depend on detecting injection in any particular language.
**Limitations.** It requires re-architecting the agent around a custom interpreter. Utility drops, and token costs and documented side channels remain. The code is unsupported research code [64]. There is no product, approval UI or audit store.
**Relevance to Mirsad.** CaMeL is the academic basis for Mirsad's taint-tracking design. Mirsad tries to approximate CaMeL-style source-to-sink policies *without* rewriting the agent, by labelling tool outputs at the proxy. Mirsad must therefore state plainly that proxy-level taint is weaker than CaMeL's interpreter-level tracking: once untrusted text enters the model's context, the proxy cannot see the model's internal data flow, and Mirsad must fall back on conservative session-level labels.

## 4. Strengths and weaknesses by product (condensed)

- **Lakera / Check Point AI Guardrails.** It is one of only two commercial detectors in the sample that list Arabic for prompt-attack screening (the other is Bedrock Guardrails, Standard tier), and its documentation covers indirect injection via tool responses and tool descriptions. Its weakness for Mirsad's use case is that it returns a verdict and leaves enforcement to the application: it has no per-parameter rules, data-flow tracking, approval or tamper-evident audit, and its agent features are early access. Its SaaS logging default needs attention under Saudi data-residency rules.
- **NVIDIA NeMo Guardrails.** It is very flexible, open source and actively maintained, with execution rails at the tool layer. Its weakness is that tool-layer security has to be programmed by hand, its documentation says tool outputs are trusted by default, and Arabic is documented only as a refusal-message language, not for injection detection.
- **Meta LlamaFirewall / Prompt Guard 2.** It is an agent-focused, layered and free defense, and AlignmentCheck (labelled experimental in the paper) audits the agent's reasoning. It is detection-only, with no deterministic authorization, approval or audit. Prompt Guard 2 has no Arabic evaluation, a 512-token window and gated licensing.
- **Azure Prompt Shields / Foundry.** It has the most explicit indirect-injection taxonomy of the cloud vendors and tool-response scanning for agents (preview), and its agent platform has approval primitives and an intent-alignment signal. On the other side, its detectors were tested only in English, the agent features are preview and Foundry-bound, and it has no taint tracking or tamper-evident audit.
- **AWS Bedrock Guardrails and AgentCore Policy.** Taken together, these are the closest commercial competitor: deterministic default-deny per-tool and per-parameter policy at a gateway, session-aware temporal rules, Arabic-optimized injection classification, and integrity-validatable CloudTrail logs. They are limited by AWS lock-in (AgentCore Gateway only; temporal rules confined to one account and Region; Guardrails-in-policy in five Regions at launch), the lack of provenance/taint labels, approval only as a policy pattern without an end-user app, and opt-in, file-level log integrity with redacted arguments.
- **Google Model Armor / Agent Gateway.** It has a free monthly allotment and low published pricing, a native MCP integration for Google servers, and default-deny egress control. It is stateless, its floor settings are project-wide, its MCP coverage is limited to Google servers, it does not test Arabic, and it has no approval or tamper-evident audit.
- **Cloudflare.** The edge firewall is model-agnostic, and MCP portals centralize tool allow-lists and logs. The firewall sees HTTP traffic to the model, not agent-to-tool flows. Its AI detection fields are a paid Enterprise add-on with no price in the documentation, its language coverage is not documented, and AI Gateway's guardrail language list excludes Arabic.
- **Protect AI LLM Guard.** It is a convenient open-source scanner suite, but it is archived, English-only for injection and limited to model I/O.
- **Invariant Guardrails / Snyk.** Its expressive rule language covers tool arguments and call sequences and is the closest prior art to Mirsad's policy engine. The open-source project's future is unclear after the acquisition and the shutdown of the hosted Explorer, and Snyk's current GA governance works only at the server level.
- **MCP gateways (Docker, agentgateway, ContextForge).** These are solid, vendor-neutral infrastructure for isolation and identity-based tool authorization; agentgateway (route-level CEL on `mcp.tool.arguments`) and ContextForge (OPA plugin) can also express argument-level rules. Their semantic security is thin: no built-in injection detection except ContextForge's optional plugin around the archived, English-only LLM Guard model, and no taint, approval or tamper-evident audit.
- **CaMeL.** It gives the strongest security guarantees through true data-flow and capability enforcement. It is a research prototype that requires re-architecting the agent, costs some utility (77% vs. 84% of AgentDojo tasks solved) and is not maintained by its authors.

## 5. Synthesis

### 5.1 Themes

1. **The industry is moving from model I/O to the tool layer.** By late 2026, Azure Foundry offers tool-call and tool-response intervention points (preview) [18], Google offers MCP floor settings and Agent Gateway [36], [37], AWS has made AgentCore Policy generally available [30], and Cloudflare, Docker and open-source projects such as agentgateway and ContextForge ship MCP gateways or portals [44], [56], [59], [62]. Mirsad's choice of deployment point matches this trend, so it is no longer a novelty in itself.
2. **Detection and enforcement are converging, but usually inside a single vendor's platform.** AWS combines a deterministic policy with a Guardrails injection signal [31]. Azure pairs Prompt Shields with an approval gate and Task Adherence [19], [21]. Lakera adds tool allow-lists to a classifier [3]. These combinations work only inside each vendor's own runtime.
3. **Data-flow (taint) security remains mostly academic.** Only CaMeL implements provenance-tracked sink policies [63]. Invariant's flow operator [50] and AWS's temporal policies [29] are sequence- or history-based approximations. No commercial product we reviewed documents taint labels on untrusted tool output.
4. **Arabic is unevenly supported and rarely evaluated.** Lakera [2] and AWS Bedrock Guardrails (Standard tier) [24] list Arabic for prompt-attack detection. Azure (tested in English only) [20], Google (not in its tested list) [35], Prompt Guard 2 (not evaluated) [16], LLM Guard (English-only) [47], Cloudflare AI Gateway (not listed) [43] and NeMo Guardrails (detector languages not stated) [10] do not. None publishes Arabic-specific accuracy figures in the pages we reviewed.
5. **Human approval is offered as a primitive, not a product.** Foundry's `require_approval` [21], Bedrock's `requireConfirmation` [26] and AgentCore's approval-as-prior-action pattern [29] all leave the approval user experience, notification delivery and reviewer identity to the developer. CaMeL warns that frequent prompts cause user fatigue [63].
6. **Audit integrity is a platform afterthought.** Among the products reviewed, only AWS documents cryptographic integrity validation, through CloudTrail digests [33], and it covers gateway invocation records with redacted arguments [32] rather than a per-decision record of policy, taint label, detector score and approver.
7. **The open-source ecosystem is unstable.** LLM Guard is archived [45], Invariant's hosted backend is shut down [52], and three detector vendors were acquired in 2025 [48], [49], [67]. A replaceable detector and an open policy format are practical requirements, not just nice extras.

### 5.2 Gap statement

As of 11 October 2026, none of the products, open-source projects or prototypes we reviewed documents, in one vendor-neutral and self-hostable component, all five of the following: (1) declarative per-tool and per-parameter policy enforced at the MCP/function-calling boundary; (2) taint labels that follow untrusted tool output to externally visible sinks; (3) an injection detector evaluated on Arabic as well as English; (4) a ready-to-use out-of-band human approval channel; and (5) a tamper-evident, per-decision audit trail. AWS AgentCore Policy covers (1) well, and (3) and (5) partially, but only inside AWS. agentgateway covers (1) in an open-source, vendor-neutral gateway (argument checks through route-level CEL authorization [59]) but none of (2)-(5). ContextForge can approximate (1) through its OPA plugin [62]. Invariant Guardrails covers (1) and part of (2), but its maintenance is uncertain. CaMeL covers (2) most rigorously, but only as a research agent architecture. **Mirsad's defensible contribution is therefore integration and localization, not a new primitive:** it combines known techniques (Cedar/Invariant/agentgateway-style policy, CaMeL-inspired taint, Lakera/Prompt-Guard-style detection, approval gates and hash-chained logging) into one open, cloud-neutral proxy, and it evaluates the result on Arabic and English indirect-injection scenarios.

### 5.3 Implications and honest limits for Mirsad

- **Position Mirsad accurately.** Do not claim that Mirsad is the only tool-layer firewall, the only system with per-parameter policy, or the only Arabic-capable detector. AWS AgentCore Policy, agentgateway, Invariant Guardrails, Lakera and AWS Bedrock Guardrails each contradict at least one of those claims.
- **Benchmark against the documented baselines.** Compare Mirsad's detector with Prompt Guard 2 86M (open), the LLM Guard DeBERTa model (English baseline) and, where free tiers or published pay-as-you-go pricing allow, Lakera, Azure Prompt Shields, Bedrock Guardrails and Model Armor, using a shared Arabic/English indirect-injection set. Report false-positive rates as well as detection rates.
- **Acknowledge that proxy-level taint is weaker than CaMeL.** A proxy cannot see the model's internal data flow, so Mirsad's labels will be session- or context-level and conservative. Measure the resulting utility cost, for example on AgentDojo-style tasks.
- **Design the approval flow against fatigue.** Use policy to keep approvals rare and high-risk only, show the taint provenance in the approval request, and record approver identity and latency in the audit log.
- **Reuse existing infrastructure where it fits.** Building Mirsad as a Docker MCP Gateway interceptor, an agentgateway ExtMCP processor or a ContextForge plugin [56], [60], [62] could reduce engineering risk and strengthen the vendor-neutrality argument.
