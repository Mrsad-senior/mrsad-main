# Appendix B – Test Reports & Validation Results

This appendix is the test case specification and test report (deliverable D5). Section 3.5 describes the test strategy. This appendix contains the evidence: the requirements traceability matrix (B.2), the specification of representative test cases in the style of ISO/IEC/IEEE 29119-3 [@iso29119_series] (B.3), the security test cases (B.4), the measured results (B.5) and the open items (B.6). Every number below is read from the result files listed in @tab:t-evidence when the document is built. A value shown as "[pending]" has not been produced yet. Python test files are under `tests/<area>/` and web test files under `web/tests/`. A test name such as `test_policy_engine.py::test_unknown_agent_is_denied` identifies one automated test function.

## B.6 Known limitations and open items

- **Detector accuracy and attack success rate are not measured yet** (B.5.8). Until they are, the evaluation shows what Mirsad costs legitimate work, but not how much protection it gives against real attacks.
- **Tests verify how detections are handled, not detection quality.** Functional tests use neutral placeholders scored by a stub rule, so they cannot show whether real Arabic or English injections are recognised.
- **All detector-dependent numbers come from the rules-only fallback**, because no trained model is packaged. The benchmark, the latency benchmark and the result false-positive rate must be measured again once a model ships.
- **No attack episode has been run.** The harness executes attack episodes (`bench/attacks.py`, tested with neutral placeholder text in `tests/bench/test_bench_attacks.py`), but no attack files exist yet.
- **Benchmark coverage is limited.** The scripted agent replays task plans exactly, the LLM run covers {{reports/results_summary.json#bench.llm_smoke.tasks}} tasks, and the oracle approver is idealised. Approval quality and decision time of real people are not modelled.
- **Usability (NFR4) and accessibility (NFR10) checks are incomplete.** The decision-time figure is an analytical Keystroke-Level Model estimate (Section 4.2.8); no approver has been timed in a user study, no acceptance session (Section 3.5.7) has been held, and no UI review checklist is recorded. Keyboard navigation and reduced-motion behaviour are not covered by automated tests.
- **Concurrency.** Tail latency with {{reports/results_summary.json#latency.separate_process.sessions}} sessions on one worker is high, and part of the waiting happens inside the gateway (B.5.4). Multi-worker and PostgreSQL latency have not been measured.
- **Deployment.** The CI workflow defines a Docker build job, but no CI run, image build or `docker compose up` is recorded in `reports/`. The Compose file does not yet set `MIRSAD_POLICY_PATH` and `MIRSAD_UPSTREAMS_PATH` for the `mirsad` service (Appendix E.2.2).
- **Coverage scope.** Only statement coverage is collected. The 80% target is not enforced by a CI threshold, and `npm audit` is not part of the CI workflow.
- **Excluded tests.** The two `llm`-marked tests are not part of the recorded run.
- **Small open integration items.** Two classes implement login throttling (`mirsad/auth.py` and `mirsad/api/routers/auth.py`) and the application uses the second, so one should be removed. The policy embedded in `demo/agent.py` for stand-alone use of the demonstration agent lacks the global rule `no-bulk-export-to-email` and should load `configs/policies/default.yaml` instead. One literal left-to-right mark remains in the Arabic dictionary of the web app, and isolate characters remain inside two JSON test fixtures captured from the server; they should be written as escapes like the Python sources.
- **Benchmark fingerprint.** The runner fingerprints the scenario files but not the policy, so a resumed run would not detect a policy change; the reported runs were therefore executed from scratch (B.1).
- **Audit integrity has a documented limit.** Someone who holds the HMAC key can rewrite history undetected unless an external anchor of the chain head is kept (TC-37).
- **Security testing is automated and internal.** No external penetration test or adaptive red-team exercise has been carried out against the gateway.
