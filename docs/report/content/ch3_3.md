## 3.3 System Design & Architecture

This section defines the design of Mirsad as built: its architecture and context, components, core processes, policy language, taint tracking, injection detector, database, security design, interfaces, user interface and deployment. The design follows the engineering contract `docs/dev/BUILD_SPEC.md` (Section 3.4.1), and every diagram was drawn from, or checked against, the code in `src/mirsad/`; the Mermaid sources are kept in `docs/diagrams/`.

Four protection principles [@saltzer1975protection] guided the design:

- **Complete mediation.** Every tool call and every tool result passes through one enforcement point.
- **Fail-safe defaults.** Unknown agents and undeclared tools are denied, and an internal error, an unavailable audit log or an unanswered approval request ends in denial.
- **Least privilege.** Permissions are granted per agent, per tool and per argument, and an agent only discovers the tools its policy allows.
- **Separation of privilege.** High-risk actions need a human approver, and the auditor role can review the audit log without being able to change policies.

### 3.3.1 Architectural style and system context

Mirsad is a **policy enforcement point (PEP)** in the sense of the XACML reference architecture [@oasis2013xacml]. The gateway (`mirsad.gateway.Gateway`) is the PEP and the `PolicyEngine` is the policy decision point; the taint tracker and the injection detector act as attribute providers that supply the provenance of the session's data and evidence about tool results; human approval is an obligation that must be discharged before an escalated call proceeds; and the audit log records every decision. Unlike a conventional PEP, Mirsad mediates in two directions. The **call path** checks what the agent wants to do before the tool runs, and the **result path** inspects what the tool returned before the model reads it, because indirect prompt injection arrives inside tool results [@greshake2023indirect].

Placing the enforcement point at the tool-calling boundary, rather than inside the model or the agent's code, was the central architectural decision. It makes Mirsad independent of the model (NFR2), requires no change to the agent apart from its tool endpoint, and governs actions rather than text. Designs that restructure the agent, such as CaMeL [@debenedetti2025camel] and the patterns of Beurer-Kellner et al. [@beurerkellner2025designpatterns], give stronger guarantees but cannot be added to an existing agent. Privilege-control systems such as Progent [@shi2025progent] are closest to Mirsad's policy layer; Mirsad adds data-flow tracking, Arabic-aware detection, human approval and a verifiable audit trail around such a layer.

@fig:d-context shows the system context. The agent calls enterprise tools through Mirsad on behalf of a business user; the attacker can only place content in systems the agent reads, such as e-mail, web pages and documents; approvers decide on their phones; and administrators and auditors work in the dashboard.

![System context: Mirsad sits between the AI agent and the enterprise tools; the attacker influences only the content stored in those tools](docs/figures/context.png){#fig:d-context width=6.0}

@fig:architecture shows the internal architecture, which combines four styles:

1. **Layers.** Protocol adapters (MCP proxy, OpenAI-compatible proxy, Guard API) translate external protocols into one internal model (`ToolCall`, `ToolResult`); the gateway core orchestrates the defence layers; storage sits underneath. A new agent protocol only touches the adapter layer.
2. **Pipes and filters.** On the call path, the policy engine, rate limiter and taint tracker each examine the call and emit `Reason` objects, which a combining step reduces to one decision. On the result path, detection, sanitising or spotlighting, and taint registration run in sequence.
3. **Publish–subscribe.** Approval events and new audit events are published on an in-process notifier and delivered over Server-Sent Events (SSE) and, optionally, Web Push.
4. **Modular monolith.** All components run in one Python process behind one FastAPI application. For a five-person team and a 200 ms latency budget (NFR1), in-process calls were preferred over separate services; typed interfaces and constructor injection (Section 3.3.2) keep the module boundaries, so a layer can later be moved out of process.

![Mirsad architecture: protocol adapters, the call path (policy engine, rate limiter, taint tracker, combining step, human approval), the result path (injection detector, sanitising and spotlighting, taint labelling) and the shared services](docs/figures/architecture.png){#fig:architecture width=6.0}

@fig:d-class shows the main classes and the shared data model. `Gateway` aggregates five runtime services; `PolicyEngine` owns its `RateLimiter`; `ApprovalService` publishes through a `Notifier`; and `UpstreamManager.call` is passed to `Gateway.execute` as the executor of allowed calls, so the gateway never needs to know how a tool is reached. The data classes (stereotype «model») are Pydantic models defined once in `mirsad/models.py`. `ToolCall` and `ToolResult` are the protocol-independent forms of a call and its result. `ToolProfile` is the security profile of one tool for one agent (allowed, trust, sensitivity, sink, risk, approval mode). A `Reason` is one piece of evidence from one layer: a machine-readable code, English and Arabic messages, a proposed `Action`, a risk score and structured evidence. A `Decision` combines the reasons with the risk score, sink, policy version, approval identifier and audit sequence number, and an `InspectionOutcome` is the verdict on a result (pass, flag, sanitize or block) with the content the model will see. `Action` is ordered (allow < require_approval < deny), and `Risk` maps a score to a level (medium from 0.3, high from 0.6, critical from 0.85). Because every layer reports in the same `Reason` type, evidence from different layers can be combined uniformly.

### 3.3.3 Core processes

**P1: deciding on a tool call.** @fig:d-seq-call shows the sequence for a call arriving through any adapter, and @fig:d-flow shows the decision logic. `Gateway.check_call` performs these steps:

1. Read the session's taint snapshot and call `PolicyEngine.evaluate_call`, which resolves the tool profile and sink and returns the policy and rate-limit reasons (Section 3.3.4).
2. Unless the agent is unknown, call `TaintTracker.evaluate_call` with the resolved sink (Section 3.3.5).
3. Combine all reasons with deny-overrides: the most severe action wins and the risk score is the highest score.
4. If the result is ALLOW but the tool's approval mode requires a human at this risk level, add `APPROVAL_POLICY` and escalate to REQUIRE_APPROVAL.
5. Append a `tool_call.decision` audit event with the call, profile, sink, all reasons, the part of the taint snapshot the rules consulted, the rate-limit counters and the risk score.
6. If approval is required, request it and wait (process P3); the final action is ALLOW only if the request is approved.
7. Record the call in the session and return the `Decision`, whose `latency_ms` excludes time spent waiting for a human.

Steps 1 to 5 run in a worker thread under one re-entrant lock, so snapshot, evaluation and audit append are atomic with respect to concurrent calls while the event loop stays free. Three fail-closed rules apply: an exception in any layer gives DENY with `INTERNAL_ERROR`; a failed audit append gives DENY with `AUDIT_UNAVAILABLE`, because no action may happen without a record; and a failed approval service gives DENY with `APPROVAL_UNAVAILABLE`. In monitor mode the would-be decision is computed and audited with `enforced: false`, but ALLOW is returned and results are not altered, so a policy can be tuned in shadow deployment before it is enforced.

![Sequence of a tool call through the gateway: decision, execution and inspection of the result](docs/figures/seq-tool-call.png){#fig:d-seq-call width=6.0}

![Decision logic for a tool call. Constraints, rate limits and global rules all report their reasons before the combining step](docs/figures/flow-check-call.png){#fig:d-flow width=2.9}

**P2: inspecting a tool result.** `Gateway.inspect_result` scans the content when the tool is marked `scan` or its results are untrusted (results of tools the policy does not allow are always untrusted), maps the score with the tool's thresholds to pass, flag, sanitize or block, spotlights untrusted content that is not blocked, registers the result with the taint tracker and appends a `tool_result.inspection` event. A sanitiser that cannot locate the suspicious text escalates to block, and a detector failure withholds the result. `Gateway.execute` composes P1 and P2: it runs the tool (with a 120 s default timeout) only for allowed calls and re-binds the result to the original call and session, so that an upstream cannot attribute its output to another call.

**P3: human approval.** @fig:d-seq-approval and @fig:d-state show the approval process and its state machine. `ApprovalService.request` stores a pending record with the redacted arguments, the decision, English and Arabic summaries and an expiry time (120 s by default), publishes `approval.requested` over SSE and, when configured, Web Push. The waiting call blocks on an event object, with a database re-check every 5 s for decisions made by another process. Every transition is a conditional `UPDATE ... WHERE status = 'pending'`, so exactly one decision wins when two approvers act at once, and a second decision is rejected with HTTP 409. At the deadline the request becomes EXPIRED, which the gateway treats as DENY; this also prevents a late approval of an action the agent was already told had been refused.

![Sequence of an escalated call: approval request, notification, human decision and resumption of the waiting call](docs/figures/seq-approval.png){#fig:d-seq-approval width=6.0}

![State machine of an approval request; every terminal state other than Approved blocks the call](docs/figures/state-approval.png){#fig:d-state width=4.2}

The approver's summary is built by `approvals/summary.py` from the reason codes and their evidence, not by a language model, so attacker-controlled text cannot rewrite it; values copied from arguments are length-limited and stripped of line breaks. Mirsad paused it because the agent read an untrusted email (read_email call_r1) earlier in this session, and this action sends data outside the organisation, and the recipient address is outside the allowed domains (najd-trading.example). The example shows a deliberate trade-off. The recipient came from the e-mail's `from` field, which the policy lists as trusted, so the rule that denies destinations chosen by untrusted text does not fire; the session-level taint rule and the domain constraint still ask a human to confirm. This is safe but adds friction to legitimate work.

**P4: audit verification and replay.** Verification recomputes the hash chain (Section 3.3.7). `Gateway.replay(seq)` loads the policy version recorded in a decision event, rebuilds the call and the stored taint snapshot, re-runs the policy with the stored rate counters (leaving the live limiter untouched) and the taint rules on the snapshot, and compares the action and reason codes; inspection events are rescanned. Because the taint rules are a pure function of the call and the snapshot, replay is exact (Section 4.2.7 reports the replay results).

Data stores D1 (policies), D2 (audit events) and D3 (approvals) are database tables. D4 (session taint state) is kept in memory per process, bounded in size and expired after six idle hours; the part of D4 a decision depends on is copied into its audit event, so the audit log, not memory, is the durable record.

### 3.3.4 Policy language design

The policy language had four goals: a policy must be reviewable by a security analyst in a pull request; permissions must default to deny and reach individual arguments; mistakes must be caught with precise messages before activation; and evaluation must be deterministic and versioned so that decisions can be replayed. General-purpose languages such as Rego [@opa_rego] or XACML [@oasis2013xacml] are more expressive, but a domain-specific YAML format with a strict Pydantic schema fits a prompt-injection policy on one page and is harder to get dangerously wrong. @tab:d-policy summarises the structure of a policy document.

Table: Structure of a policy document (schema version 1) {#tab:d-policy widths=1.1,2.9,2.2}
| Element | Keys | Meaning |
|---|---|---|
| Document | `version`, `mode` (enforce or monitor), `organization` (`name`, `internal_domains`) | Schema version; shadow mode; domains inside the organisation |
| `defaults` | `decision` (deny, allow or require_approval), `approval_timeout_s` | Treatment of unmatched tools (deny by default); time a human has to decide |
| `detector` | `flag_threshold`, `block_threshold`, `on_detect` (sanitize, block or flag), `spotlight` | Global detector settings; agents and tools can override them |
| `taint` | `enabled`, `destination_params`, `trusted_fields`, one action per taint rule | Data-flow settings (Section 3.3.5); agents can override them |
| `agents[]` | `id`, `name`, `description`, `tools` (tool key → tool entry) | One entry per agent identity; `id` equals the agent's `policy_agent_id` |
| Tool entry | `allow`, `trust`, `sensitivity`, `sink` (none, internal, external or dynamic), `sink_params`, `risk`, `approval` (never, on_risk or always), `scan`, `constraints`, `rate_limit`, `detector` | Security profile of one tool for one agent |
| Constraint | `max`, `min`, `max_length`, `min_length`, `enum`/`in`, `not_in`, `pattern`, `not_pattern`, `domain_in`, `domain_not_in`, `max_items`, `required`, `type`, `on_violation` | Checks on one argument, combined with AND; a violation denies or requires approval |
| `rules[]` | `id`, `when` (`tool`, `agent`, `arg_matches`, `sink`, `session_tainted`, `min_risk`), `action` | Global rules evaluated after the tool entries |

The excerpt below, from the tool entries of `configs/policies/default.yaml`, shows how the business rules of Section 3.2 are expressed: e-mail outside the organisation needs approval (BR4), exports are capped at 50 records (BR3), payments always need approval (BR2), and unlisted tools are denied (BR1).

```yaml
send_email:
  allow: true
  sink: dynamic
  sink_params: [to, cc, bcc]
  risk: medium
  constraints:
    to:      {domain_in: [najd-trading.example], on_violation: require_approval}
    body:    {max_length: 20000}
  rate_limit: {max_calls: 20, per_seconds: 3600}
get_customer:     {allow: true, sensitivity: confidential, scan: true}
export_customers:
  allow: true
  sensitivity: confidential
  scan: true
  risk: high
  approval: on_risk
  constraints:
    count: {max: 50, on_violation: deny}
  rate_limit: {max_calls: 3, per_seconds: 3600}
transfer_funds:   {allow: true, risk: critical, approval: always, sink: external,
                   constraints: {amount_sar: {max: 10000, on_violation: deny}}}
"*":              {allow: false}
```

CRM results are trusted and confidential, but they are scanned (`scan: true` on `search_customers`, `get_customer` and `export_customers`), because their free-text notes can contain text that came from web forms or customer e-mails; a detection relabels the result as untrusted (Section 3.3.5).

**Resolution.** For a tool name the engine selects the exact key, otherwise the longest matching glob, otherwise the catch-all `"*"`, otherwise `defaults.decision`; equal-length globs that can match the same name are rejected as ambiguous. A `dynamic` sink is EXTERNAL if any recipient or URL in the destination arguments has a domain outside `internal_domains` or no recognisable domain, INTERNAL if all destinations are internal, and NONE if there is none.

**Evaluation and combining algorithm.** `PolicyEngine.evaluate_call` collects reasons in a fixed order: (1) an unknown agent is denied and evaluation stops; (2) a tool that is not allowed is denied and evaluation stops; (3) an informational `TOOL_RISK` reason carries the tool's risk score (0.1, 0.3, 0.6 or 0.9 for low to critical); then (4) every argument constraint, (5) the sliding-window rate limit, (6) every matching global rule and (7) `approval: always`. After step 3 nothing short-circuits, so the audit log and the approver see every objection. The gateway adds the taint reasons and applies **deny-overrides**: for the reasons r1, …, rn of a call, the final action is the most severe among them (deny > require_approval > allow) and the risk score is the maximum of their scores. The approval mode is applied last: `always` escalates every call; `on_risk` escalates when the combined risk is at least 0.6, or when the tool's own risk is high or critical and a taint rule objected; `never` does not escalate, although a deny still denies. Deny-overrides is monotonic, so adding a layer, constraint or rule can only make a decision stricter. The accepted limitation is that an `allow` rule cannot create an exception to a deny; exceptions are written as narrower deny rules. @tab:d-reasons lists the reason codes outside the taint layer, whose codes are given in Section 3.3.5.

Table: Reason codes of the policy, detector, approval and system layers {#tab:d-reasons widths=1.9,0.9,1.5,1.9}
| Code | Layer | Action | Risk score |
|---|---|---|---|
| `UNKNOWN_AGENT`, `TOOL_NOT_ALLOWED` | policy | deny | 0.5 |
| `TOOL_RISK` | policy | allow (informational) | 0.1 / 0.3 / 0.6 / 0.9 |
| `CONSTRAINT_VIOLATION` | policy | the constraint's `on_violation` | 0.5 |
| `RATE_LIMIT` | ratelimit | deny | 0.5 |
| `RULE_MATCH` | policy | the rule's `action` | rule's score, else 0.5 (0 for allow) |
| `APPROVAL_ALWAYS` | policy | require approval | the tool's risk score |
| `APPROVAL_POLICY` | approval | require approval | combined score |
| `APPROVED_BY_HUMAN`, `DENIED_BY_HUMAN`, `APPROVAL_EXPIRED` | approval | allow, deny, deny | unchanged |
| `INTERNAL_ERROR`, `AUDIT_UNAVAILABLE`, `APPROVAL_UNAVAILABLE` | system, approval | deny (fail closed) | 1.0 |
| `MONITOR_MODE` | system | allow (records the would-be action) | 0 |
| `INJECTION_SUSPECTED`, `INJECTION_DETECTED` | detector | deny when the result is blocked; otherwise allow, with the result flagged or sanitised | detector score |
| `SCAN_FAILED` | detector | deny (result withheld, fail closed) | 1.0 |
| `RESULT_TRUNCATED` | system | allow (informational) | 0 |

**Safe validation.** The schema is strict: unknown keys, operators and duplicate YAML keys are errors, with "did you mean" suggestions and the YAML line and column. Because policy regular expressions run against arguments written by a possibly hijacked model, the validator rejects patterns with nested ambiguous quantifiers, the classic cause of catastrophic backtracking (ReDoS); at run time at most 50,000 characters reach a policy regex, and a truncated input counts as a rule match, so the check fails closed.

**Versioning and hot reload.** A policy's version is the SHA-256 hash of the canonical JSON of the parsed document, so formatting does not change it but any semantic change does. Every version is stored, and the version in force is recorded in every audit event. Engines are immutable: activation swaps in a new engine atomically, and an evaluation in progress keeps the engine it started with.

### 3.3.5 Taint-tracking design

An LLM can mix any input into any output, so taint cannot be propagated through the model, and the guarantees of language-based information-flow control are out of reach [@sabelfeld2003language]. Mirsad therefore tracks data at the boundary it controls, in the style of dynamic taint analysis [@newsome2005dynamic]: tool results are **sources**, tool calls are **sinks**, and the rules look for the combination of private data, untrusted content and external communication that makes an agent exploitable [@willison2025trifecta]. The approach follows information-flow control for agents [@costa2025fides; @wu2024fsecure], except that a violation can be routed to a human approver instead of always aborting.

**Labels.** Every result receives two labels from its tool profile, as in Denning's lattice model [@denning1976lattice]: integrity (trusted or untrusted, where untrusted means a third party can control the content) and confidentiality (public < internal < confidential). Detector evidence overrides declared trust: a result labelled as an injection is registered as untrusted even if its tool is declared trusted. Each recorded value also carries a `trusted_field` flag for fields vouched for by the producing system rather than the content's author, such as the sender, identifier and date of a received e-mail. This separates "reply to the sender", which is normal, from "send to an address written in the body", the typical exfiltration pattern.

**Two granularities.** At **session level**, a session that has read untrusted content stays tainted for the rest of its life, a conservative but sound assumption. At **value level**, recognisable values are extracted from every result with their source tool, call and field: e-mail addresses, URLs, domains, IBANs, phone numbers, numbers of at least six digits, record identifiers and, for confidential results only, hashed word 8-grams of long text. Results and arguments are canonicalised the same way (Unicode NFKC, invisible characters removed, Arabic-Indic digits converted, case folded, Saudi mobile numbers unified), so a value matches whatever its spelling. N-grams are hashed with BLAKE2b, which keeps them stable across processes for replay and avoids storing the text. @tab:d-taint lists the four rules evaluated before every call.

Table: Taint rules evaluated for each tool call {#tab:d-taint widths=2.1,2.9,1.3,0.7}
| Rule (reason code) | Fires when | Default action | Risk |
|---|---|---|---|
| `TAINT_UNTRUSTED_TO_EXTERNAL` | The session has read untrusted content and the call's sink is external | require approval | 0.6 |
| `TAINT_CONFIDENTIAL_TO_EXTERNAL` | An argument contains a value recorded from a confidential result and the sink is external (sending customers only their own record is exempt) | require approval | 0.7 |
| `TAINT_UNTRUSTED_DESTINATION` | A destination argument (recipient, URL, IBAN, webhook) or its domain first appeared in untrusted content outside a trusted field, and never in a trusted result; the organisation's own domains are excluded | deny | 0.9 |
| `TAINT_AFTER_INJECTION` | An injection was detected earlier in the session and the tool's risk is high or critical | require approval | 0.8 |

Every taint reason names the source tool, call and field of the matching value, so the approver sees where the data came from. State is bounded (at most 2,000 values per session; sessions dropped after six idle hours), and the rules are one pure function of the call, profile, sink, settings and a read-only view of the session, used by both live evaluation and replay.

The coarse session-level rule is the price of soundness; Section 4.2.4 measures the approval friction it causes. Value-level matching, in turn, can be defeated by paraphrasing or re-encoding data, which is why the session-level rule and human approval remain as a backstop.

### 3.3.6 Injection detector design

The detector reads untrusted tool results and the results of tools marked `scan: true`, such as CRM records, whose free-text notes can contain text that came from outside the organisation. It is designed as a **signal, not a security boundary**, because adaptive attacks have bypassed published detectors with high success rates [@nasr2026attackermovessecond]; the policy and taint layers are built to block harmful actions even when the detector misses. The detector catches common cases cheaply, drives the result-path actions, arms `TAINT_AFTER_INJECTION` and gives approvers and auditors readable evidence. It works in six stages:

1. **Normalisation.** HTML entities are decoded; zero-width and bidirectional control characters removed; text converted with NFKC and lower-cased; Arabic diacritics (tashkeel) and elongation (tatweel) removed; alef, ya and ta marbuta variants and Persian look-alikes unified; digits converted to ASCII; Cyrillic, Greek and Armenian look-alikes in Latin words folded; and letter-spaced words joined. Obfuscation is reported as *signals*, and an offset map takes each span back to the original text, so highlights and sanitising point at the characters the user and the model see.
2. **Language identification** (English, Arabic, mixed or other, including Arabizi), for reporting and per-language evaluation only.
3. **Rules.** 158 weighted regular-expression rules in YAML: 76 English, 51 Arabic (Modern Standard Arabic and Gulf, with some Egyptian and Levantine forms), 7 Arabizi and 24 language-independent rules for structural tricks such as chat-template tokens, hidden HTML, markdown-image exfiltration and encoded blobs. The rule score combines the best weight of each distinct rule by noisy-OR, and evasion signals raise it only when a rule has fired, because ordinary Arabic text produces some of them.
4. **Model.** Hashed character 2- to 5-grams (2^20 features) and word 1- to 2-grams (2^18 features) feed a class-balanced logistic regression. Texts are scored over windows of 600 characters with a stride of 300 and the highest window probability is kept, so one injected sentence in a long e-mail is not diluted.
5. **Ensemble.** The score is a noisy-OR of model score m and rule score r, 1 − (1 − m)^α (1 − r)^β, calibrated so that the operating point chosen on the validation split (highest F1 with a false-positive rate of at most 5%) maps to 0.5; the policy defaults (flag at 0.5, block at 0.8) keep their meaning after retraining.
6. **Persistence without pickle.** The model is stored as plain arrays and JSON metadata, loaded with `allow_pickle=False` and checked for shape and finite values; if it is missing or invalid, the detector runs in rules-only mode instead of failing.

A linear model over hashed n-grams was chosen over a fine-tuned transformer because the detector runs inline on CPU, the team's dataset is small, and character n-grams tolerate Arabic morphology, spelling variation and Arabizi (Section 3.4.5). On the result path, scores below the flag threshold pass, scores between the thresholds are flagged and audited, and higher scores trigger the tool's `on_detect` action. Sanitising widens each span to its sentence or line and replaces it with a bilingual marker; a positive detection without a span fails closed and the content is withheld. Untrusted content that reaches the model is spotlighted [@hines2024spotlighting]: it is wrapped in delimiters whose boundary is derived from a SHA-256 hash of the call identifier, source and content, so the content cannot contain its own closing marker, and a bilingual note tells the model to treat it as data.

The packaged detector currently contains no trained model and runs in rules-only mode, which is also the mode recorded by the latency benchmark (`{{reports/results_summary.json#latency.separate_process.detector_mode}}`). The F1 scores on the held-out English and Arabic test sets (target 0.85) are produced by running `make detector` after the team has added its labelled data as described in `docs/detector.md`, and Section 4.2.2 reports them. The attack-labelled data, like the attack files of Mirsad-Bench (`bench/scenarios/attacks/README.md`), is written by the team (Section 3.6.4).

### 3.3.7 Database design

Persistence uses SQLAlchemy 2.0 with typed declarative mappings and only portable column types, so the same schema runs on SQLite in development and PostgreSQL 16 in deployment. SQLite connections enable foreign keys and write-ahead logging, so dashboard readers never block the audit writer. Timestamps are UNIX epoch seconds stored as floats, matching the Pydantic models. @fig:erd shows the six tables.

![Entity-relationship diagram of the six tables. The solid line is the only enforced foreign key; dashed lines are logical references by value](docs/figures/erd.png){#fig:erd width=6.0}

Only `push_subscriptions.user_id` is an enforced foreign key (to `users.id`, with cascading delete). The other relationships are logical references by value: `audit_events.agent_id` and `approvals.agent_id` hold an agent's policy identifier; `approvals.decided_by` and `policies.created_by` hold usernames; `audit_events.policy_version` holds a `policies.version`; an approval and the audit events of its call share the `call_id`; and each event's `prev_hash` equals the previous event's hash. These references are deliberately not enforced: the audit log is append-only evidence that must outlive the deletion or renaming of what it mentions, and its hashes cover values exactly as written, so a cascading delete or a blocked insert would destroy or prevent evidence.

The management tables are in third normal form. Three columns hold JSON documents by design (`audit_events.payload_json`, `approvals.decision_json`, `approvals.arguments_json`): their shape depends on the event type and they must be stored verbatim to be hashed and replayed, while frequently filtered fields are promoted to indexed columns. An approval copies the agent, tool and arguments of its call, so the record shows exactly what the approver saw. @tab:d-tables is the table dictionary.

Table: Data dictionary of the database tables {#tab:d-tables widths=1.2,1.6,1.9,1.5}
| Table | Purpose | Key and constraints | Written by / read by |
|---|---|---|---|
| `users` | People who sign in | `id` primary key; `username` unique; role restricted to admin, approver, auditor; language to en, ar | Administrators / authentication, user management |
| `push_subscriptions` | Browser push endpoints per user | `id` primary key; `endpoint` unique (HTTPS only); `user_id` foreign key with cascade | Approver PWA / Web Push delivery |
| `agents` | Agent identities and key hashes | `id` (slug) primary key; `key_prefix` indexed; only the SHA-256 hash of the key is stored | Administrators / agent authentication |
| `policies` | Every policy version stored | `version` (SHA-256) primary key; `active` indexed | Policy activation / gateway start-up, replay, administrators, auditors |
| `audit_events` | Hash-chained log of decisions, inspections, approvals, administrative changes and logins | `seq` primary key assigned by the writer (no auto-increment); seven indexes | `AuditLog.append` only / administrators, auditors, statistics, replay |
| `approvals` | Approval requests and outcomes | `id` primary key; indexes on `status`, `created_at`, `call_id` | Approval service / approvers, administrators, waiting calls |

**Hash-chain design.** Each event is a link in a chain built from HMAC-SHA-256 [@rfc2104], following the hash linking of Haber and Stornetta [@haber1991timestamp] and the secure audit log of Schneier and Kelsey [@schneier1999secure]:

```text
hash(n)      = HMAC-SHA256(K_audit, prev_hash(n) + "|" + canonical_json(event(n) without "hash"))
prev_hash(n) = hash(n-1),   prev_hash(1) = "0" * 64
K_audit      = HMAC-SHA256(secret_key, "mirsad/audit-hmac/v1")
```

Canonical JSON uses sorted keys, no whitespace and UTF-8, so Arabic text is hashed as written. The hashed body contains every stored column, including `seq` and the indexed columns, so editing any field breaks the chain, and the audit key is separate from the JWT signing key although both derive from the server secret. Before hashing, `redact()` removes credentials and masks Saudi national ID and Iqama numbers, IBANs and card numbers to their last four characters (Section 3.6.1), so secrets never enter the chain; payloads are limited to 20,000 characters while keeping their structure. There is one writer per process: under a lock it reads the head and inserts `seq = head + 1` in the same transaction, and if another process takes that number first, the primary key rejects the insert and the writer retries.

Verification walks the table in sequence order and reports the first broken event: a gap in `seq` reveals a deletion, a `prev_hash` that does not link reveals an insertion or reordering, and an HMAC mismatch reveals a modification or a hash forged without the key. The same function verifies an unfiltered JSON export offline. A rewrite by someone holding the key, and truncation of the newest events, cannot be detected from the chain alone; for both, `AuditLog.anchor()` returns the current head to be stored outside the database, and verifying against an earlier anchor detects them. Because enforced calls are refused when the append fails, no action can happen without an event.

### 3.3.8 Security design and threat model

A firewall concentrates trust, so the gateway itself is a target. Tests ST-01 to ST-23 are in `tests/security/test_gateway_security.py`; other entries name the test modules of the component concerned.

These tests verify the gateway's own defences. Whether the design stops hijacked agents is measured by the reduction in attack success rate on Mirsad-Bench relative to an unprotected agent (target at least 80%; Section 4.2.3), once the team adds its attack files to `bench/scenarios/attacks/` (Section 3.6.4).

### 3.3.9 Interface design

Mirsad has three kinds of external interface: agent interfaces, a REST and streaming interface for people, and the command line. The agent interfaces differ in who executes the tool, which determines the strength of enforcement (@tab:d-agent-if). In **inline** interfaces Mirsad executes the tool itself, so a denied call cannot run. In **advisory** interfaces the agent runtime executes tools and Mirsad removes or refuses denied calls; this protects against a manipulated model but assumes the agent's own code is honest, so inline interfaces are recommended when the runtime is not trusted.

Table: Agent-facing interfaces {#tab:d-agent-if widths=1.4,2.3,1.1,1.6}
| Interface | Transport | Tool executed by | Enforcement |
|---|---|---|---|
| MCP proxy | stdio (`mirsad mcp-proxy`) or streamable HTTP at `/mcp` | Mirsad | Inline |
| Tool invocation | `POST /v1/tools/{tool}/invoke`, `GET /v1/tools` | Mirsad | Inline |
| OpenAI-compatible proxy | `POST /v1/chat/completions` | Agent runtime | Advisory: denied calls removed from the model's response |
| Guard API and Python SDK | `POST /v1/guard/tool-call`, `POST /v1/guard/tool-result`; `MirsadClient.guard()` | Agent runtime | Advisory: the SDK raises `MirsadBlocked` before the tool runs |

**MCP proxy.** One MCP server is built per agent. `tools/list` returns only the tools the agent's policy allows, and every `tools/call` goes through `Gateway.execute`. Any refusal or internal failure returns an MCP error result with a bilingual explanation whose reason texts are clipped, so a block message cannot re-inject a long attacker-controlled value into the model's context. Only inspected text is returned; MCP structured content is never forwarded, because the sanitiser does not rewrite it.

**OpenAI-compatible proxy.** For each request the proxy (1) replaces every `role: tool` message with its inspected version, (2) removes tool definitions the policy does not allow, (3) forwards the request to the configured LLM endpoint without the agent's key, and (4) checks every returned tool call, removing denied calls, appending a bilingual explanation and setting `finish_reason` to `stop` when no call remains. Streaming is rejected, because a tool call must be complete before it can be checked.

**REST and streaming API.** People authenticate with a JWT from `POST /api/auth/login`; agents use their API key in the `Authorization` or `X-Mirsad-Key` header. Agent keys are rejected on `/api/*` and user tokens on `/v1/*`. @tab:d-api groups the endpoints. Bodies are JSON, errors have the form `{"detail": ...}`, status codes follow HTTP semantics (401, 403, 404, 409 for a conflicting decision or duplicate, 413 for bodies over 1 MB, 422, 429), and an OpenAPI description is generated from the typed models. Live updates use SSE on `GET /api/stream`, read with `fetch` and an `Authorization` header so that tokens never appear in URLs. The `mirsad` command line covers operations that should not depend on the web interface, such as policy activation, audit verification, export and replay, and agent and user creation.

### 3.3.10 User-interface design

Mirsad has two front ends built from one React and TypeScript code base: the **administration dashboard** at `/` and the installable **approver PWA** at `/approve`. They share the API client, live-stream reader, translation dictionaries, explanation components and design tokens, and the gateway serves both from its own origin, so a strict content security policy that allows only same-origin scripts holds. The interface follows these principles:

1. **Plain language first, evidence on demand.** A request opens with three short sections, *What the agent wants to do*, *Why Mirsad paused it* and *Where the data came from*, followed by the raw arguments, collapsed by default. This applies the human–AI interaction guidelines of explaining why the system acted and supporting efficient correction [@amershi2019guidelines]. Only escalated calls reach a human, to limit the alert fatigue and complacency that automation research warns about [@parasuraman2000model].
2. **Bilingual and right-to-left by design.** Every string exists in English and Modern Standard Arabic with the same keys, which tests enforce. Choosing Arabic sets the document's language and direction, and CSS logical properties mirror the whole layout without separate stylesheets. Identifiers such as tool names, addresses, hashes and YAML stay left-to-right inside isolation elements, and server messages are bilingual at the source (`message_ar`, `summary_ar`).
3. **Accessibility to WCAG 2.2 level AA** [@w3c2023wcag22]. Pages use semantic landmarks; every control has a label; everything works from the keyboard; dialogs trap and restore focus; live regions announce new requests; colour is never the only signal; contrast is checked by a test; reduced-motion preferences are respected; and touch targets in the approver app are at least 44 × 44 pixels.
4. **Safe, deliberate actions.** Approve and Deny open a confirmation sheet that restates the consequence and takes an optional note; the buttons are disabled when a request has expired or the phone is offline; API keys and generated passwords are shown once; and text from agents and tools is always rendered as text, never as HTML.
5. **Speed for the approver.** The target is a decision in under 30 seconds on a phone (NFR4): pending requests are sorted by soonest expiry with a countdown, and a push notification opens the request directly.

The dashboard has ten pages (Overview, Activity and audit, Approvals, Policies, Agents, Users, Tools, Detector playground, Demo console, Settings); the sidebar shows only the pages the signed-in role may use, and the API rejects any request outside that role. @fig:d-ui-audit shows the audit-event drawer with its hash-chain fields and replay and verification actions, and @fig:d-ui-policies-ar shows the policy editor in Arabic with the mirrored layout. @fig:d-ui-pwa-pending and @fig:d-ui-pwa-detail show the approver app's pending list in Arabic and a request in English. The screenshots were taken from the running system with the simulated workspace; Appendix C contains the complete set.

### 3.3.11 Deployment architecture and technology stack

@fig:d-deployment shows the deployment architecture. The reference deployment is a Docker Compose stack on one server or virtual machine:

- **`mirsad` container.** A multi-stage image in which a Node.js stage builds the web applications and a Python 3.12 stage installs the gateway. It runs as a non-root user, keeps its data in a `/data` volume, exposes port 8700 and has a health check on `/healthz`.
- **`db` container.** PostgreSQL 16 with its own volume and readiness check; the gateway is configured to start only when the database is ready. Development and the benchmark use SQLite instead.
- **Ollama container (optional).** Enabled with the `demo` profile to serve Qwen2.5-7B for the demonstration agent.
- **Upstream tools.** Declared in `configs/upstreams.yaml` as in-process MCP servers, subprocesses over stdio, or remote servers over streamable HTTP.

Agents connect over HTTPS with their API key, and browsers and phones over HTTPS with a JWT. TLS is terminated by a reverse proxy in front of the container, which is not part of the Compose file; HTTPS is mandatory for the approver PWA. The Redis node in the figure marks an optional extension for sharing rate-limit counters between replicas and is not implemented: rate limits are kept in memory per process (Section 3.4.5), which fits the single-node scope. Configuration comes from `MIRSAD_` environment variables or a `.env` file (database URL, server secret, approval timeout, Web Push keys, CORS origins, demonstration switch); a missing secret is generated and stored in an owner-only file.

The Compose files are written but have not been executed, because Docker was not available on the build machine (Section 4.1.1), and the policy and upstream paths must be set explicitly for the `mirsad` service (Appendix E.2.2).

![Deployment architecture: the Mirsad container, the database, optional components and the clients](docs/figures/deployment.png){#fig:d-deployment width=6.0}

The design targets one node serving at least 50 concurrent agent sessions (NFR11) with a median added latency of at most 200 ms (NFR1); Chapter 4 reports the measured latency (Section 4.2.5). Scaling beyond one node would require moving rate-limit counters and session taint state into a shared store, which is future work. The technologies of each layer and the reasons for choosing them are given in the technology-stack table of Section 3.4.4.
