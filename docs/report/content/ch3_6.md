## 3.6 Ethical, Legal & Security Considerations

### 3.6.1 Data privacy and the PDPL

Mirsad is designed so that the security tool does not itself become a privacy risk. The Saudi Personal Data Protection Law [@ksa2021pdpl] requires that personal data be processed only for a legitimate purpose, minimised, protected against unauthorised disclosure, and that breaches be reported. The design responds as follows:

- **Synthetic data only.** All customers, e-mails, documents and bank accounts in the demonstration workspace and in Mirsad-Bench are fictional; e-mail addresses and web sites use the reserved `.example` domain, and phone numbers and IBANs are clearly fake. The detector dataset contains no real personal data.
- **Masking in the audit log.** Before an event is hashed and stored, secrets (API keys, bearer tokens, JWTs, passwords, private keys) are removed and personal identifiers (Saudi national ID numbers, IBANs, payment-card numbers) are masked to their last four characters. The log keeps its forensic value (which tool, which destination, which decision) without becoming a second copy of customer data.
- **Purpose limitation.** Taint tracking stores only the identifying values needed to recognise a data flow (addresses, identifiers, hashed n-grams) and expires idle sessions.
- **Breach prevention as a primary goal.** The taint rule "confidential data to an external sink" exists specifically to prevent the kind of unauthorised disclosure the PDPL penalises.

### 3.6.2 Regulatory and standards alignment

Appendix A maps the system's controls to the NCA Essential Cybersecurity Controls [@nca2024ecc] (event logging and monitoring, identity and access management, cybersecurity in third-party and cloud services), to the OWASP Top 10 for LLM Applications [@owasp2024llmtop10] (LLM01 prompt injection, LLM02 sensitive information disclosure, LLM06 excessive agency), to the NIST AI RMF functions [@nist2023airmf] and to SDAIA's AI ethics principles [@sdaia2025aiethics]. Human approval of high-risk actions implements the principles of human oversight and accountability; the audit log and decision replay implement transparency and explainability towards auditors.

### 3.6.3 Security of the gateway itself

A firewall concentrates trust, so it becomes a target. The STRIDE analysis (Section 3.3.8) produced security requirements that are built into the gateway. Agents authenticate with per-agent API keys stored only as SHA-256 hashes, and people with salted scrypt password hashes and short-lived JWTs under role-based access control (admin, approver, auditor). Failed logins are throttled and audited, every response carries security headers, and request bodies are size-limited. Regular expressions in policies are validated and their input is bounded to limit denial-of-service risk. The audit log is HMAC-chained, so undetected modification requires the server's secret key, and approval requests fail safe: expiry means denial. The gateway was tested with its own security test suite, static analysis and dependency scanning (Section 4.2.6).

### 3.6.4 Responsible handling of attack material

Evaluating a prompt-injection defence requires attack material, which is dual-use: it helps defenders test systems but could also help attackers. This report contains no attack payloads or attack templates, and the automated tests use neutral placeholders wherever content must be scored as an injection (Section 3.5.1). The only injected instructions in the repository are the short illustrative texts of the eight Demo Console scenarios (`demo/scenarios.py`), which address the simulated workspace and its reserved `.example` addresses and are used only for live demonstration. The attack material needed for the evaluation, namely the attack-labelled detector batches and the Mirsad-Bench attack files, is written and reviewed by team members, is used only against the project's simulated workspace and fictional organisation, and is not reproduced in this report, which publishes only aggregate metrics. Whether that material is released, and in what form (for example with restricted access), will be decided after the review, following the practice of public benchmarks such as AgentDojo [@debenedetti2024agentdojo]. No attack is run against any third-party system or service.

### 3.6.5 Social and professional considerations

- **Approver workload.** The approval workflow is designed to ask humans only about high-risk actions, with a short plain-language summary in their preferred language, to avoid alert fatigue and rubber-stamping.
- **Inclusiveness and accessibility.** The dashboard and approval app are fully bilingual (Arabic with right-to-left layout, and English) and follow WCAG 2.2 basics (keyboard navigation, labels, sufficient contrast, no colour-only signals).
- **Honest claims.** Prompt injection is not a solved problem; detectors can be evaded by novel phrasings. The report presents Mirsad as one layer of defence in depth, reports false positives, approval friction and limitations openly, and marks every unmeasured result, including detection misses and attack success, as pending (Chapters 4 and 5).
- **Professional codes.** The team followed the principles of the ACM Code of Ethics and Professional Conduct [@acm2018code] on avoiding harm, honesty, respecting privacy and accepting professional review.

### 3.6.6 Licences, third-party components and AI assistance

All third-party software used by Mirsad is open source. Almost all runtime dependencies use permissive MIT, BSD or Apache-2.0 licences (e.g. FastAPI, SQLAlchemy, scikit-learn, React and the MCP SDK); the Web Push library pywebpush uses the weak-copyleft MPL-2.0 licence, which permits use in an Apache-2.0 project as long as the library itself is distributed unmodified with its source available. The full list is in `docs/THIRD_PARTY.md`; the public `deepset/prompt-injections` dataset (Apache-2.0) is planned as an optional external English test set, to be downloaded by the team. Mirsad itself is released under the Apache-2.0 licence. The Qwen2.5 model used for the demonstration agent is used under its published licence.

In line with the proposal's commitment and university policy, the team discloses that **an AI coding and writing assistant (Anthropic's Claude) was used during the project** to help generate source code and tests, draft documentation and report text, author parts of the benign synthetic Arabic/English dataset batches and the benign benchmark user tasks, and produce diagrams. The assistant was not used to write the attack material for the evaluation (the attack-labelled detector batches and the Mirsad-Bench attack files); that material is written and reviewed by team members (Section 3.6.4). AI-assisted outputs were treated like any other contribution: they were checked by the automated test suite, the evaluation results come only from actual executions of the system, every literature reference was verified against its original source, and the team members remain responsible for the originality, correctness and understanding of all submitted work.
