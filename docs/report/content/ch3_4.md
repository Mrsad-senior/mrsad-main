## 3.4 Implementation Strategy

### 3.4.1 Development methodology

The team's agreed working method is **Scrum** [@schwaber2020scrum]: two-week sprints, a product backlog, sprint reviews in the bi-weekly supervisor meetings and a short retrospective at the end of each sprint. Its working rules build security activities into every sprint rather than leaving them to the end (a DevSecOps approach): threat modelling during design, review of every pull request by a second member, automated tests, linting, static analysis and dependency scanning in continuous integration, and a dedicated security-testing sprint before the final evaluation. Investigation, requirements, design, implementation and testing are iterated inside sprints, and the Senior Project I prototype (milestone M3) is the first planned complete increment.

The build was organised around a written **engineering contract** (`docs/dev/BUILD_SPEC.md`) that fixes the public interface of every component (names, arguments, return types, REST endpoints and database tables) before implementation starts. Because each workstream owns separate packages and codes against the contract, the five workstreams can be developed in parallel; shared data types live in a single module (`mirsad/models.py`) owned by the integrator, and Section 4.1.13 lists the integration issues that remained.

### 3.4.4 Development environment, tools and version control

All code is kept in a single Git repository. The agreed working rules are a protected main branch, feature branches, and pull requests that need one review and a green CI run before merging. The continuous-integration workflow (GitHub Actions, `.github/workflows/ci.yml`) defines three jobs (Section 3.5.4): a Python job with linting (Ruff), the test suite with coverage, static application security testing (Bandit) and dependency vulnerability scanning (pip-audit); a web job with the TypeScript type check, the web unit tests and a production build; and a Docker image build that runs after both. No CI run is recorded in `reports/`.

### 3.4.5 Changes from the proposal and their justification

Engineering judgement led to five deliberate changes from the tools listed in the proposal. Each keeps the proposal's objectives intact.

1. **Installable progressive web app instead of Flutter for the approval app.** A PWA built with the same React code base as the dashboard installs to the home screen on Android and iOS, supports system notifications and offline caching, avoids app-store registration fees and review delays, and could be built and tested on the team's machines. Wrapping it as a store app (Capacitor or Flutter) remains possible future work.
2. **Classical detector instead of fine-tuning XLM-RoBERTa / CAMeLBERT.** The latency budget (NFR1), CPU-only deployment and the size of the team-built dataset favour a character n-gram linear model combined with weighted rules. It is designed to run in milliseconds on a CPU (target below 10 ms for a 2 KB text, measured once a model is trained), and its features are inspectable. Fine-tuning a multilingual encoder is planned as an optional second stage (Chapter 5).
3. **SQLite and PostgreSQL without Redis.** Rate limits are kept in memory per gateway process; Redis would only be needed for multiple replicas, which are out of scope.
4. **Standard Web Push (VAPID) instead of Firebase Cloud Messaging.** Web Push is an open standard supported by the PWA and avoids a dependency on a proprietary service.
5. **Own benchmark harness (Mirsad-Bench) instead of running AgentDojo directly.** AgentDojo's environments are English-only and its standard runs assume hosted model APIs. Mirsad-Bench reuses its methodology (user tasks × injection tasks, attack success rate and utility) on a simulated Saudi enterprise with Arabic scenarios and runs fully offline. Burp Suite and OWASP ZAP were likewise replaced by an automated security test suite that can run in CI (Section 4.2.6).
