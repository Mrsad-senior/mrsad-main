## 3.5 Testing & Validation

This section explains how Mirsad is verified, meaning that it is built correctly against its specification, and validated, meaning that it does its job of stopping hijacked agents without getting in the way of legitimate work. It covers the test strategy, the test levels and tools, the entry and exit criteria, the continuous-integration pipeline, the metrics, the test inventory and the planned user acceptance testing. The test case specification, the requirements traceability matrix (@tab:rtm) and the full test report are in Appendix B. Section 4.2 discusses the results.

### 3.5.1 Test strategy

The strategy uses the concepts and documentation structure of ISO/IEC/IEEE 29119 [@iso29119_series] and is organised as a V-model. Each development artefact on the left of the V has a test level on the right that checks it (@tab:t-levels). The requirements in Section 3.2 are checked by end-to-end tests and by the benchmark. The architecture and the engineering contract (`docs/dev/BUILD_SPEC.md`) are checked by integration and API tests, and the design of each package by unit tests. The test design followed three principles.

1. **Requirement-driven and risk-based.** Every functional and non-functional requirement is traced to at least one automated test (@tab:rtm). Most effort went to the parts whose failure would either let an attack through or block legitimate work: the policy engine, the taint rules, the fail-closed paths of the gateway, the approval workflow and the audit chain.
2. **Negative cases are first-class.** Every rule has a case where it must fire and a case where it must not. The bulk-export rule is tested at 50 and 51 recipients (boundary values). Each constraint operator is tested with one passing and one violating value (equivalence classes). The legitimate counterpart of an "untrusted destination" is a reply to the sender of an e-mail, and that reply must not be blocked. The security suite attacks the gateway itself with forged tokens, database tampering and path traversal.
3. **Deterministic and offline.** Tests use temporary SQLite files, seeded synthetic data (the fictional Najd Trading Co. on reserved `.example` domains), explicit timestamps for rate-limit windows, and fake components where a unit has to be isolated. Tests that need the local language model carry the pytest marker `llm` and are left out of the default run, because model output is not stable enough to serve as a pass/fail gate.

**Test data and attack material.** This report contains no prompt-injection text, and apart from the eight Demo Console scenarios (`demo/scenarios.py`), which the demo tests load to check that they plant their text into the simulated workspace (Section 3.6.4), neither does the repository. A test that needs content to be scored as an injection uses a neutral placeholder marker together with a stub detector rule. Everything that happens after the detector produces its score, that is thresholds, sanitising, spotlighting, taint registration, audit and replay, then runs the production code. These tests therefore show how Mirsad *handles* a detection. They do not show how *well* the detector detects real attacks. Detector accuracy and attack success rate are measured separately, once the team's attack-labelled data is complete (Section 3.5.6).

### 3.5.2 Test environment, tools and responsibilities

All recorded runs were made on a team member's laptop (Apple silicon, macOS) with Python 3.12 and Node.js. The CI workflow is configured to run the same suites on Linux; no CI run is recorded in `reports/`. Python tests use pytest with pytest-asyncio and pytest-cov. HTTP-level tests drive the FastAPI application through httpx, either in memory or over a real socket served by uvicorn. The PostgreSQL tests start a throwaway server from the `pgserver` package, so no database has to be installed. Web tests use Vitest with Testing Library and jsdom. The `llm`-marked tests and the LLM smoke run use Qwen2.5-7B [@qwen2024qwen25] served locally by Ollama.

Each workstream owner writes and maintains the unit and API tests for their own packages (Section 3.4.3). The security suite, Mirsad-Bench and the latency benchmark belong to the security-testing and benchmark workstream (Abdulmalik bin Saedan). Under the agreed working rules, every pull request needs a second reviewer and a passing CI run before it is merged (Section 3.4.4).

### 3.5.3 Entry and exit criteria

A test level starts only when its entry criteria hold:

- **Unit and API tests:** the public interface of the component is fixed in the engineering contract and the code passes the linter.
- **Integration and end-to-end tests:** the unit suites of every package involved pass.
- **Benchmark runs:** the scenario files validate (`python -m bench.loader`) and the full automated suite passes, so that benchmark numbers always come from tested code.
- **Reported results:** the evidence pipeline (Section 3.5.4) has been run on the version being reported.

The lint and type-check gate is enforced by the CI workflow, but its result is not stored with the evidence, so it is shown as not recorded. The last two are project success criteria that cannot be measured until attack data exists. They are reported as open rather than estimated.

### 3.5.4 Continuous integration and the evidence pipeline

The CI workflow (`.github/workflows/ci.yml`) is configured to run on every pull request and every push to the main branch. @tab:t-ci shows its three jobs. A failing step stops the job, and under the agreed working rules a pull request is not merged with a red build. No CI run is recorded in `reports/`, so the results in this report come from the local evidence pipeline described below.

Table: Continuous-integration jobs {#tab:t-ci widths=0.8,3,2.2}
| Job | Steps | The build fails when |
|---|---|---|
| python | Install the project with development extras; `ruff check` on source, tests, demo, bench and scripts; `pytest -m "not llm"` with coverage; `bandit -r src`; `pip-audit` | any lint finding, failing test, Bandit finding or vulnerable dependency |
| web | `npm ci`; `tsc --noEmit`; Vitest; production build with Vite | a type error, failing test or build error |
| docker | Build the container image (runs only after both other jobs pass) | the image does not build |

Two checks are not yet enforced by CI. The 80% coverage target is read from the coverage report rather than enforced with a `--cov-fail-under` threshold, and `npm audit` runs in the evidence pipeline and in `make security` but not in the workflow.

The numbers in this report come from a separate **evidence pipeline**, `scripts/run_evidence.sh`. It re-runs the Python suite (writing JUnit XML and a coverage JSON file), the web suite, Bandit, pip-audit and npm audit, both latency benchmarks and both scripted Mirsad-Bench runs (through `scripts/run_bench.sh`), and it trains the detector when labelled data is present. `scripts/collect_results.py` then gathers every result into `reports/results_summary.json`. The report builder (`scripts/build_docs.py`) reads each number in this document from that file when the document is generated. A number in the text therefore cannot drift away from the evidence, and a value that has not been produced yet prints as "[pending]" instead of being estimated.

### 3.5.5 Metrics

The following metrics are collected. Definitions of the benchmark metrics follow `docs/benchmark.md`.

- **Test execution:** number of tests per area, and passed, failed and skipped counts. A test is one pytest item or one Vitest case, so each parametrised case counts separately.
- **Code coverage:** statement coverage of the `mirsad` package. Branch coverage is not collected.
- **Static analysis and dependencies:** number of findings per tool, and number of packages with a known advisory.
- **Latency:** *added latency* per call, which is the HTTP round trip through Mirsad minus the direct in-process tool call, paired call by call. It is reported as p50, p95 and p99, together with throughput and HTTP errors. Time spent waiting for a human is excluded by design.
- **Benchmark:** *utility*, the share of episodes whose success predicate holds. *Benign false-positive rate (FPR)*, the share of benign calls denied automatically. *Approval friction*, the share of benign calls handed to a human. *Final block rate*, the share of benign calls that did not run in the end. *Result false-positive rate*, the share of benign tool results that the detector sanitised or blocked. *Approval recall*, the share of tasks that legitimately need approval in which a human was asked. *Gateway latency*, the decision plus result inspection per call. *Attack success rate (ASR)*, and *ASR reduction* = 1 − ASR(defence) / ASR(none).
- **Audit integrity:** the result of hash-chain verification and the share of decisions whose replay gives the same action.
- **Detector:** precision, recall, F1, false-positive rate and ROC-AUC on each held-out split, and scan latency for a 2 KB text.
- **Usability (NFR4):** an analytical estimate of approval time with the Keystroke-Level Model [@card1980klm] (Section 4.2.8). Approval times of real users have not been measured yet.
- **Acceptance:** for each acceptance scenario of Section 3.5.7, whether each participant accepts it, with the number of participants.

FPR and friction are reported separately on purpose. A policy can deny no benign call and still cost a lot of human time if it escalates too often, and the two numbers show these two costs.

### 3.5.7 User acceptance testing

The levels above verify the system against its specification. User acceptance testing validates it with the people it is built for: whether an approver, an administrator and an auditor can complete their main tasks with the real interfaces and accept the result. @tab:t-uat lists the planned acceptance scenarios. They are run in the simulated Najd Trading Co. workspace with prepared, benign requests, by the supervisor and two to three security practitioners recruited by the team, each of whom records "accept" or "reject" per scenario with a reason. Section D of the questionnaire in Appendix F is completed after the session. No session has been held yet; outcomes will be reported with the number of participants, and no result is estimated before then.
