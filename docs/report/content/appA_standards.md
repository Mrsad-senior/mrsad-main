# Appendix A – Standards & Constraints Matrix

This appendix records how Mirsad relates to the standards, regulations and guidelines that apply to an AI-agent security gateway deployed in Saudi Arabia (@tab:a-standards), and how the project handled its technical, economic, time, legal, ethical, social, environmental and accessibility constraints (@tab:a-constraints).

Two points govern how the first table should be read. First, Mirsad supports an organisation's compliance but does not make it compliant: conformity with ISO/IEC 27001, ISO/IEC 42001, the NCA Essential Cybersecurity Controls or the PDPL is a property of the organisation's management system, processes and deployment, not of one software component. Second, the evidence column cites only artefacts that exist in the repository or in `reports/`, and lists as *gaps* the provisions that the current version does not yet cover. Those gaps feed the future work in Section 5.5.

The gaps in @tab:a-standards share a pattern. Mirsad already produces the evidence that the standards ask for (decisions, reasons, approvals, verifiable logs), but the surrounding operational features (retention and archival, SIEM forwarding, ATLAS tagging, erasure) are still to be built. These features are needed before an organisation could rely on Mirsad's logs in an NCA ECC or PDPL assessment.

## A.2 Constraints Matrix

Table: Project constraints and how they were handled {#tab:a-constraints widths=1.1,1.9,2.6,1.7}
| Constraint type | Constraint | How it was handled | Remaining effect |
|---|---|---|---|
| Technical | Personal laptops without GPUs; a young and fast-changing MCP specification; a latency budget of 200 ms per tool call | Local open-weight model (Qwen2.5-7B through Ollama) for the demonstration agent and the LLM benchmark runs<br>CPU-only detector (weighted rules plus a linear n-gram model)<br>Protocol handling isolated in an adapter layer built on the MCP Python SDK v2<br>Added latency measured in every evidence run | Measurements come from one laptop and a single server process; the transformer detector and multi-replica deployment are future work |
| Economic | Student budget set in the proposal | Free, open-source stack; local models instead of paid APIs for development and evaluation; a PWA instead of store apps, which avoids developer-account fees<br>The proposal's 1,660 SAR budget was revised to 1,185 SAR, with price evidence and a zero-cost fallback, in the D2 work plan and budget | Paid model APIs and cloud hosting are needed only for an optional confirmatory run and a public demonstration |
| Time | Two semesters; five students, each owning one workstream | Contract-first design (`docs/dev/BUILD_SPEC.md`) so that workstreams could proceed in parallel<br>Two-week sprints with MoSCoW priorities<br>A scripted evidence pipeline (`scripts/run_evidence.sh`) that regenerates every result | Lower-priority items deferred to future work (Section 5.5) |
| Legal | PDPL, NCA ECC, software and dataset licences | Synthetic data only, with reserved `.example` domains<br>Masking of personal identifiers in the audit log<br>Permissive open-source dependencies; Mirsad licensed under Apache-2.0<br>Attacks are run only against the project's own simulated workspace | The detector dataset's datasheet (`data/detector/DATASHEET.md`) is still to be written by the data authors |
| Ethical | Dual-use attack material; honest reporting; use of an AI assistant | Attack material for the evaluation is to be authored and reviewed by team members only and is not reproduced in this report (Section 3.6.4); the demonstration scenarios contain only short illustrative instructions aimed at the simulated workspace<br>Results that have not been measured are shown as pending, never estimated<br>AI assistance disclosed (Section 3.6.6) | Detector F1 and attack success rate stay pending until the team adds its data |
| Social | Approvers' workload and alert fatigue; Arabic-speaking users and approvers | Escalation only on policy-defined high-risk paths<br>Plain-language summaries in Arabic and English<br>Persona-driven design (Section 1.5.1) | Approver workload and comprehension not yet measured with real users |
| Environmental and sustainability | Energy use of AI components; long-term maintainability of the software | No GPU training; the detector is designed to scan a text in milliseconds on a CPU (target below 10 ms for a 2 KB text, measured once a model is trained)<br>Development inference ran on the team's existing laptops<br>Documented, tested open-source code base that others can maintain | Energy consumption was not measured |
| Accessibility | Users with different abilities, languages and devices | WCAG 2.2 AA basics in both web applications<br>Full right-to-left Arabic interface; dark theme; reduced motion<br>Approver app designed to install from the browser on Android and iOS without an app store | No automated accessibility audit yet; Web Push delivery not yet tested on real phones |
