# Chapter 2 – Literature Review

This chapter reviews the work that Mirsad builds on. Section 2.1 surveys previous studies by theme, Section 2.2 compares existing products and research systems with Mirsad, and Section 2.3 states the gap that Mirsad addresses and the limits of its contribution.

The sources come from six research tracks compiled by the team and fact-checked against primary records (publisher pages, arXiv, standards bodies, official repositories and vendor documentation) on 11 October 2026. Numbers quoted from papers are the values their authors report; the team has not reproduced them, and they are tied to model versions that age quickly. Products are described only as their documentation describes them. Preprints and practitioner blogs are cited where they are the original or most current record of an influential result.

## 2.1 Overview of Previous Studies

### 2.1.1 LLM agents and tool use

An LLM agent couples a language model with tools that it can invoke. ReAct [@yao2023react] established the pattern that most agent frameworks follow: the model alternates between free-text reasoning and actions, and the observation returned by each action is fed into the next reasoning step. On two decision-making benchmarks, ReAct with one or two in-context examples beat imitation- and reinforcement-learning baselines by 34 and 10 absolute points of success rate. Toolformer [@schick2023toolformer] showed that a model can learn, with little human annotation, when to call an external API, which arguments to pass and how to use the result. Both papers treat tool use as a capability problem, and neither has a threat model for tool outputs: ReAct assumes that observations are honest, and Toolformer's tools are read-only. Nothing in the reason-act-observe loop separates data returned by a tool from instructions, which is the root cause of indirect prompt injection.

Two interfaces carry this loop in practice. OpenAI-style function calling lets the model emit a tool name and JSON arguments that the host application executes. The Model Context Protocol (MCP) [@mcp2026spec] standardises discovery and invocation across independent servers: a host uses clients to connect over JSON-RPC 2.0 to servers that expose tools, resources and prompts. The current revision (2026-07-28) is stateless, so each request carries its own protocol version and capabilities. The specification is direct about security. Clients must treat tool annotations as untrusted unless they come from a trusted server, there should always be a human able to deny a tool call, and clients should show tool inputs to the user, validate tool results before passing them to the model and log tool usage for audit. It also says that the protocol cannot enforce these principles and leaves them to implementers. Mirsad can be read as an implementation of these client-side recommendations, placed outside the host so that it works for any agent.

Tool use also does not work equally well in every language. In what its authors describe as the first benchmark of Arabic tool calling, accuracy fell by roughly 5–10% on average when the user wrote in Arabic, whether the tool descriptions were in Arabic or English [@kubrak2025arabictools]. Lower accuracy means more malformed or unexpected tool arguments, which per-parameter checks catch whatever their cause.

### 2.1.2 Prompt injection: origins and taxonomy

Willison named the attack class in September 2022 [@willison2022prompt]. He compared it with SQL injection: applications build prompts by concatenating trusted instructions with untrusted input, and the model cannot tell where one ends and the other begins. He suggested that a real fix might resemble parameterised queries but doubted that it was feasible with current architectures. Perez and Ribeiro [@perez2022ignore] gave the first systematic study, using their PromptInject framework against GPT-3, and defined two goals that later work adopted: *goal hijacking*, in which the model abandons its task for one chosen by the attacker, and *prompt leaking*, in which it reveals its hidden instructions.

The decisive step for agents was *indirect* prompt injection. Greshake et al. [@greshake2023indirect] showed that an attacker who never interacts with the model can plant instructions in content that an LLM-integrated application retrieves later, and that the retrieved text can then steer which external APIs the application calls. They built a taxonomy of consequences that includes data theft and self-propagating injections, and demonstrated attacks on Bing's GPT-4-based chat and on code-completion tools. Liu et al. [@liu2024formalizing] formalised an attack as turning the data of a *target task* into compromised data that carries an *injected task*, showed that earlier techniques are special cases of this framework, and combined them into a stronger attack. Mirsad-Bench mirrors this framing: each attack episode pairs a benign user task with an injection task. OWASP ranks prompt injection first (LLM01) among risks to LLM applications [@owasp2024llmtop10], and NIST's taxonomy of adversarial machine learning treats indirect injection as an attack made possible by control over resources that the model reads [@vassilev2025ai1002].

Across these sources, attacks can be classified on three largely independent axes, summarised in @fig:taxonomy. The *channel* is how the malicious text reaches the model: typed by the user (direct injection), planted in data that the agent reads (indirect injection), or hidden in tool metadata. The *technique* is how the attacker obtains compliance. The *goal* is what the attacker wants the agent to do. For a tool-using agent, the goals that matter most are data exfiltration, which needs a flow from a private source to a sink that the attacker can reach, and tool misuse, in which legitimate tools are called with harmful arguments. Indirect injection is the channel Mirsad is built for, because it lets an outsider borrow the user's own privileges, data and tools.

MCP has added channels of its own. Invariant Labs disclosed *tool poisoning* [@invariant2025toolpoisoning], in which an MCP server hides instructions in a tool description that the model reads in full but the user usually does not see. The same disclosure described *shadowing*, where one server's description changes how the agent uses another server's trusted tool, and *rug pulls*, where a description changes after the user has approved it. A later case study [@invariant2025github] described a "toxic agent flow" through the official GitHub MCP server: an issue in a public repository led an agent to copy information from the owner's private repositories into a public pull request. No tool was compromised; the harm came from combining trusted tools with untrusted input. The authors also observed that users often switch tool confirmations to "Always Allow", which argues for asking a human only about risky calls.

Willison's "lethal trifecta" [@willison2025trifecta] condenses the exfiltration risk: an agent that has access to private data, is exposed to content an attacker controls and can communicate externally can be told to read secrets and send them out, and MCP makes it easy for users to assemble all three without realising it. The risk has already appeared in production. EchoLeak [@reddy2025echoleak] was a zero-click flaw in Microsoft 365 Copilot in which one crafted e-mail caused Copilot to leak internal data. The exploit evaded Microsoft's cross-prompt-injection classifier, bypassed link redaction with reference-style Markdown and used images that the client fetched automatically. Two lessons from EchoLeak shaped Mirsad: a dedicated injection classifier was bypassed in a deployed product, and the fix the authors propose, provenance-based access control, is in effect taint tracking.

### 2.1.3 Benchmarks for agent security

Benchmarks have moved from text tasks, where success is judged on the model's output, to agents whose success is judged on changes to an environment. @tab:litsummary summarises the studies that most influenced Mirsad's evaluation.

BIPIA [@yi2025bipia], presented as the first benchmark for indirect injection, found all 25 models tested vulnerable and traced the weakness to models that cannot distinguish informational context from instructions. InjecAgent [@zhan2024injecagent] moved to tool-using agents. It separates *direct harm* through a tool from *data stealing*, a two-step pattern in which private data is first read and then transmitted; the second pattern is exactly the source-to-sink flow that taint tracking is designed to break. AgentDojo [@debenedetti2024agentdojo] replaced fixed test cases with a stateful environment in which success is checked by code against the environment's state, and reports utility, utility under attack and targeted attack success rate (ASR) together. Two of its baseline results are central to Mirsad's design. A *tool filter*, which restricts the agent to the tools a task needs, cut targeted ASR for GPT-4o to about 7% while keeping benign utility (73%, against 69% with no defence). A *prompt-injection detector* reached similar security (about 8%) but cut benign utility from 69% to 41.5%, and utility under attack from 50% to 21.1%, because of false positives. The authors also note that a tool filter fails when the tools a task needs are enough for the attack, as in 17% of their cases. Later benchmarks extended the attack surface to agent memory and planning [@zhang2025asb], web agents [@evtimov2025wasp] and MCP tool metadata [@wang2026mcptox; @zhang2026msb]. In MCPTox the harm is carried out through *legitimate* tools, which is why constraining the parameters of every tool matters more than blocking a suspicious one.

Large red-teaming exercises show that static benchmarks overstate robustness. NIST's Center for AI Standards and Innovation extended AgentDojo with remote-code-execution, database-exfiltration and phishing tasks. Red-teaming with the UK AI Security Institute raised ASR from 11% for the strongest baseline attack to 81%, and running each attack 25 times instead of once raised average success from 57% to 80% [@nist2025hijacking]. A public competition on *concealed* attacks, in which a harmful action is taken while the final reply looks normal, produced 8,648 successful attacks from about 272,000 attempts against 13 frontier models; every model was vulnerable [@dziemian2026ipi]. When an attack is concealed, the user cannot see it in the chat transcript, so an independent record of tool calls becomes necessary.

### 2.1.4 Defences at the model, prompt, runtime and architecture levels

Published defences work at four levels, which differ in what an organisation deploying an agent can actually adopt.

**Model level.** These defences train the model to give less weight to instructions that arrive in data. The instruction hierarchy [@wallace2024instruction] defines a priority order (system above user above tool output) and trains the model to ignore conflicting lower-priority instructions. SecAlign [@chen2025secalign] treats the problem as preference optimisation and reports ASR below 10% even against optimisation-based attacks, at a cost of two to three points on a general-knowledge benchmark. Such defences raise the baseline for everyone who uses the model, but they need the provider's cooperation or open weights and GPU fine-tuning, and they give no guarantee. An organisation that connects a hosted model to MCP servers cannot apply them.

**Prompt level.** Spotlighting [@hines2024spotlighting] marks untrusted text before it enters the context, by delimiting it, interleaving a marker character through it or encoding it, and tells the model to treat the marked text as data. With GPT-3.5 and GPT-4 it reduced ASR from over 50% to under 2% with little loss of task performance, and Microsoft offers the encoding variant as a preview option of Prompt Shields [@azure-prompt-shields]. Its authors did not test adaptive attackers, and its effect on Arabic script, where marker characters interact with word shape and diacritics, has not been studied.

**Runtime detectors.** Classifiers screen user input, tool outputs or tool calls. Meta's Llama Prompt Guard 2 [@meta2025promptguard2] is an 86M-parameter classifier with a 512-token window whose model card lists eight supported languages, none of them Arabic, and names vulnerability to adaptive attacks as a limitation. Protect AI's DeBERTa classifier [@protectai2024debertav2] handles English only and is no longer maintained. PIGuard [@li2025piguard] addressed *over-defence*: on 339 benign sentences full of words common in injections, leading guard models fell to roughly 60% accuracy. Among commercial services, Lakera Guard (now Check Point AI Guardrails) screens tool responses and tool descriptions and states coverage of more than 100 languages, Arabic among them [@lakera-prompt-defense], while Microsoft states that Azure Prompt Shields was tested with English only [@azure-region-limits-language]. The only open Arabic model found, Ara-Prompt-Guard [@namaa2025araprompguard], was trained on 33,000 machine-translated examples, supports Modern Standard Arabic (MSA) only and has no paper or independent evaluation.

The evaluation literature is consistent about detectors. Hackett et al. [@hackett2025bypassing] evaded six deployed detectors, among them Azure Prompt Shield and Protect AI's models, with character-level tricks such as zero-width characters, homoglyphs, bidirectional text and diacritics; one technique reached 100% evasion against every guardrail on each threat type it was tested on. Nasr et al. [@nasr2026attackermovessecond] scaled up gradient, reinforcement-learning, search-based and human red-teaming attacks against twelve recent defences and bypassed most with over 90% success, including Spotlighting (above 95%) and Meta-SecAlign, a successor of SecAlign (96%). PIGuard was the most resistant detector at 71%. Stacking several detectors did not stop adaptive attacks, and many successful triggers did not look malicious, so they could not be caught without also flagging benign inputs.

**Runtime frameworks and policy enforcement.** NeMo Guardrails [@rebedea2023nemo] wraps an LLM application in programmable rails written in Colang. Its authors say it should not be used as a standalone safety solution, and its documentation warns that tool results are trusted by default [@nemo-tools-integration]. LlamaFirewall [@chennabasappa2025llamafirewall] combines Prompt Guard 2, an experimental auditor of the agent's reasoning and a scanner for generated code; on AgentDojo it reduced ASR from 17.6% to 1.75%, while utility fell from 47.7% to 42.7%. Two runtime systems enforce rules instead of classifying text. AgentSpec [@wang2026agentspec] provides a rule language of trigger, predicate and enforcement, with a pause for human inspection as one enforcement action, and prevented unsafe executions in over 90% of code-agent cases with millisecond-level overhead. Progent [@shi2025progent] applies least privilege through default-deny rules over tool names and arguments, can run as a proxy in front of LLM and MCP endpoints, and sends requests to widen privileges to an approver; it reports AgentDojo ASR falling from 39.9% to 1.0%. Neither system tracks data flow, so neither can tell whether an allowed outbound call carries content supplied by an attacker.

**Architecture level.** These designs restructure the agent so that untrusted data cannot change its control flow. CaMeL [@debenedetti2025camel] has a privileged LLM write a restricted program from the trusted request alone, a quarantined LLM parse untrusted data without tool access, and an interpreter attach capabilities (provenance and allowed readers) to every value and check policies before each tool call. It completes 77% of AgentDojo tasks with provable security, against 84% for an undefended agent. FIDES [@costa2025fides] labels data for integrity and confidentiality, propagates the labels conservatively through the planner and enforces two generic policies: consequential tools run only from a trusted context, and egress tools send data only to recipients allowed to read it. When a policy is violated, FIDES aborts. Beurer-Kellner et al. [@beurerkellner2025designpatterns] generalised these ideas into six design patterns, such as plan-then-execute, while warning that human confirmation is often burdensome and prone to fatigue. A 2026 position paper [@xiang2026architecting] argues that system-level defences should form the skeleton of agentic systems, with learned models confined to constrained roles and human interaction reserved for ambiguous cases.

For Mirsad, the review leads to the following conclusions. First, detectors are useful signals but weak boundaries: every classifier tested against adaptive attackers was bypassed, and over-defence becomes alert fatigue when a flag triggers a human approval. Second, the strongest results since 2024 come from designs that ask whether an action is allowed given where its inputs came from, rather than whether a text looks malicious. Third, those designs are costly to adopt: CaMeL and FIDES require the agent to be rebuilt. Among the research designs reviewed, only Progent's proxy mode brings deterministic tool-call enforcement to unmodified agents; Section 2.2 shows that some gateway products now do the same for rules on tools and arguments.

### 2.1.5 Multilingual and Arabic LLM safety

Safety behaviour learned mainly from English data does not transfer evenly to other languages, scripts and dialects. Yong et al. [@yong2023lowresource] machine-translated harmful instructions into twelve languages and found that low-resource languages, combined, bypassed GPT-4's safeguards about 79% of the time, whereas MSA had a bypass rate of only 3.65%. Deng et al. [@deng2024multilingual] built MultiJail, unsafe prompts translated by native speakers into nine languages with Arabic among them, and showed that deliberately combining a harmful instruction with a multilingual prompt raised unsafe output to 80.92% for ChatGPT and 40.71% for GPT-4. The most directly relevant result comes from Al Ghanim et al. [@alghanim2024arabizi]. GPT-4 and Claude 3 Sonnet mostly refused harmful prompts written in standard Arabic script but produced unsafe output when the same prompts were written in Latin transliteration or Arabizi, the chat style that uses digits such as 3 and 7 for Arabic letters. The authors attribute this to refusal behaviour tied to particular written forms of words. MSA alone is therefore not the hard case; the less standard forms that Saudi users actually type are.

Arabic safety benchmarks matured quickly in 2025 and 2026, and they point the same way. SalamahBench [@abdelnasser2026salamahbench] wrote 8,270 harmful prompts in MSA and five regional varieties, including Saudi Arabic, and found robustness across varieties to depend strongly on the model. ArabicDialectSafety [@zaghouani2026arabicdialectsafety] showed that a fine-tuned MARBERTv2 encoder (macro-F1 0.95 on binary safety classification) outperformed prompted frontier LLMs, although its dialects do not include Gulf Arabic. ASAS [@abed2026asas] found obfuscation-based attacks the most effective against Arabic-capable models, and poor agreement between an LLM judge and human annotators. All of these benchmarks measure harmful *requests* to a model; none contains instructions hidden in tool outputs that try to hijack an agent.

Work on Arabic prompt *injection* is sparse. In the only indirect-injection study found that includes Arabic, instructions hidden in about 500 academic papers changed LLM review outcomes when written in English, Japanese or Chinese but had little or no effect in Arabic [@theocharopoulos2025multilingual]. The authors do not explain the result, which may reflect weaker instruction-following in Arabic rather than stronger defences; as Arabic-capable models improve, Arabic injections should be expected to become more effective. MIPIAD [@muhtadi2026mipiad] is the closest published design to a multilingual detector of indirect injection, combining a small Qwen2.5 classifier with lexical features (best F1 0.9205), but it was evaluated only on synthetic English and Bangla data.

For the detector itself, the CAMeLBERT study [@inoue2021camelbert] found that how closely an Arabic encoder's pre-training variety matches the task data matters more than the amount of pre-training data, which is a concern for Gulf dialect and Arabizi. Mirsad's first detector therefore uses character n-grams with a linear model, combined with weighted Arabic and English rules, including rules for Gulf dialect and Arabizi. Before scoring, a normalisation step removes diacritics, elongation and invisible or bidirectional control characters, and folds letter variants, digits and look-alike characters, in response to the evasion techniques above. The choice favours CPU latency and inspectable features. The model is implemented but has not yet been trained on the team's labelled data, so the packaged detector currently runs its rules only; fine-tuning an Arabic encoder is planned as a second stage (Chapter 5).

### 2.1.6 Standards and Saudi regulation

International frameworks now agree on the controls that agents need. Under LLM01, OWASP's Top 10 for LLM Applications [@owasp2024llmtop10] recommends constraining model behaviour, validating outputs with deterministic code, enforcing least privilege, requiring human approval for high-risk actions and segregating untrusted content, and notes that it is unclear whether fool-proof prevention exists. OWASP's Top 10 for Agentic Applications for 2026 [@owasp2025agentictop10] adds risks specific to agents, including agent goal hijack (ASI01) and tool misuse and exploitation (ASI02). NIST's AI Risk Management Framework [@nist2023airmf] organises AI risk work into the Govern, Map, Measure and Manage functions, and NIST AI 100-2e2025 [@vassilev2025ai1002] recommends designing systems on the assumption that injection will happen, for example by giving access to untrusted data only through well-defined interfaces. With the MCP specification, these documents agree on least privilege, complete mediation, separation of untrusted content, human approval and logging. None of them enforces anything.

Saudi regulation adds concrete obligations. The NCA's Essential Cybersecurity Controls (ECC-2:2024) [@nca2024ecc] apply to government entities and operators of critical national infrastructure. Control 2-2-3 requires least privilege, need-to-know and segregation of duties; 2-12-3 requires event logging, continuous monitoring and log retention of at least 12 months; and 4-1 covers third-party cybersecurity, under which third-party MCP servers fall. The Personal Data Protection Law (PDPL) [@ksa2021pdpl], in force since September 2023, requires technical measures to protect personal data (Article 19), requires breaches to be notified (Article 20) and restricts transfers outside the Kingdom (Article 29); its Implementing Regulation [@sdaia2023pdplregs] sets a 72-hour window for notifying SDAIA of a breach that could cause harm. SDAIA's AI Ethics Principles [@sdaia2025aiethics] include privacy and security, reliability and safety, fairness, and accountability, and its Generative AI Guidelines for Government [@sdaia2025genaigov] require human review of generative-AI output and keep data classified as restricted or higher out of these tools. These obligations sit within the digital-government goals of Vision 2030 [@ksa2016vision2030]. None of the Saudi documents mentions AI agents or tool calls, so an organisation that deploys agents has to translate them into technical controls itself. ### 2.1.7 Foundations used by Mirsad

**Information-flow control and taint tracking.** Denning's lattice model [@denning1976lattice] binds every object to a security class and allows a flow only if it respects the ordering of the classes. Labels are combined with a join, so data tends to become more restricted over time, a problem known as label creep. Sabelfeld and Myers [@sabelfeld2003language] surveyed language-based enforcement of noninterference and discussed declassification, the controlled release of information to a lower class. Newsome and Song [@newsome2005dynamic] introduced dynamic taint analysis of unmodified software, with the source, propagation and sink vocabulary that later systems use. All three assume a program whose flows can be analysed. An LLM is opaque and may mix any input into any output, so Mirsad cannot claim noninterference and applies taint at the boundary between tool results and tool calls instead. A session becomes tainted once it has read untrusted content, which is sound but coarse, as in FIDES. Recognisable values such as e-mail addresses, IBANs and record identifiers are tracked back to the result they came from, which is precise but incomplete. Human approval acts as an explicit, logged declassification step.

**Reference monitors.** Saltzer and Schroeder's design principles [@saltzer1975protection] justify the gateway architecture: complete mediation (every tool call passes through the gateway), fail-safe defaults (unlisted tools are denied), least privilege (rules per tool and parameter) and separation of privilege (a human approves high-risk calls).

**Tamper-evident logging and policy languages.** Schneier and Kelsey [@schneier1999secure] combined hash chains with message authentication codes for forensic audit logs and stated the limits of any such scheme: entries written after a compromise cannot be protected, and cryptography can detect deletion but not prevent it. Mirsad's audit log chains events with HMAC-SHA-256 [@rfc2104]. Because HMAC is symmetric, whoever holds the key could rewrite the chain, and truncation of the newest entries can only be detected against a copy of the head hash kept outside the gateway. For policy, XACML 3.0 [@oasis2013xacml] separates the policy enforcement point from the policy decision point and the attribute sources that inform it, resolves conflicts with combining algorithms, and lets a decision carry obligations. In Mirsad the gateway is the enforcement point and the YAML policy engine the decision point; the taint tracker and detector supply attributes, and "require approval" behaves like an obligation.

**Threat modelling and human-AI interaction.** Shostack's method of data-flow diagrams with trust boundaries and STRIDE threat categories [@shostack2014threat] structures Mirsad's threat model (Section 3.3.8). For the approval workflow, Amershi et al. [@amershi2019guidelines] give 18 validated guidelines for human-AI interaction, among them making clear why the system acted and supporting efficient correction and dismissal. Parasuraman et al. [@parasuraman2000model] show that automation can be set to different levels for analysis, decision and action, and warn that supervising automation brings complacency and workload problems. Mirsad therefore automates analysis and decision for most calls and asks a human only about calls that its policy marks as high-risk.

The systems in the table fall into five groups, each with characteristic strengths and weaknesses.

**Screening services and classifiers** (Lakera, Azure Prompt Shields, Google Model Armor, Bedrock Guardrails, Prompt Guard 2, LLM Guard) are easy to adopt, and two of them (Lakera and the Standard tier of Bedrock Guardrails) are the only products in the sample that document Arabic coverage. However, they return a verdict and leave enforcement to the application, they are bypassed by adaptive attackers (Section 2.1.4), and most were tested only in English. Hosted services also receive every prompt and tool output, which matters under the PDPL's rules on transfers outside the Kingdom.

**Guardrail frameworks** (NeMo Guardrails, LlamaFirewall) are open source and layered, but security at the tool layer has to be programmed by hand, NeMo trusts tool results by default, components that call an LLM add latency and can themselves be injected, and neither documents an approval workflow or a durable audit store.

**Cloud agent platforms** (AWS AgentCore Policy, Azure Foundry). AgentCore Policy is the closest commercial analogue to Mirsad: deterministic, default-deny Cedar policies on tool names and input parameters outside the agent's code [@aws-agentcore-policy], temporal conditions on session history such as requiring an earlier approval action [@aws-agentcore-temporal], and CloudTrail log files that can be validated with chained, signed digests [@aws-cloudtrail-integrity]. However, it enforces only on traffic routed through an AgentCore Gateway in AWS, documents no provenance labels, models approval as a policy pattern rather than an application for approvers, and offers only opt-in, file-level log integrity. Azure Foundry offers per-tool allow-lists and an approval gate for MCP tools but leaves the approver's interface and the audit trail to the developer [@azure-foundry-mcp].

**MCP gateways** (Docker MCP Gateway, agentgateway, IBM ContextForge) are vendor-neutral, open-source infrastructure with container isolation, tool authorisation and, in agentgateway and ContextForge, rules on tool arguments. None documents taint tracking, an approval channel or a tamper-evident log, and the only documented injection filter wraps the archived English-only LLM Guard model. They are possible hosts for a component like Mirsad rather than complete alternatives to it.

**Research policy and information-flow systems** (Progent, AgentSpec, Invariant Guardrails, CaMeL, FIDES) give the strongest guarantees. CaMeL and FIDES track data flow precisely, and AgentSpec shows that deterministic rule enforcement, including a pause for human inspection, adds only millisecond-level overhead. On the other hand, CaMeL and FIDES require the agent to be rebuilt, at a cost in utility; Progent, AgentSpec and Invariant's sequence rules do not track where a value came from; research code is often unmaintained; and none of them evaluates the approval interface or documents a tamper-evident record.

Model-level defences such as SecAlign are absent from the table because they are properties of a model rather than components an organisation can deploy. They complement a gateway: a hardened model lowers the rate of attacks that reach the tool boundary, and the gateway contains the ones that do.

## 2.3 Research Gap and Positioning

The review supports six observations. Detectors and model-level defences are bypassed by adaptive attackers [@nasr2026attackermovessecond], so a classifier cannot be the security boundary. The strongest system-level guarantees require the agent to be rebuilt [@debenedetti2025camel; @costa2025fides], while deployable tool-layer controls enforce rules on tools and arguments but do not track provenance [@shi2025progent; @aws-agentcore-policy]. Arabic is barely covered, and no Arabic benchmark of indirect injection against tool-using agents was found. Human approval is offered as a primitive rather than a product, and its interface is not evaluated [@beurerkellner2025designpatterns]. Audit integrity is an afterthought: only AWS documents cryptographic log validation, at the level of log files. Finally, the MCP specification and Saudi regulations state obligations but leave their enforcement for agents to implementers [@mcp2026spec; @nca2024ecc; @ksa2021pdpl].

**Gap statement.** As of October 2026, none of the products, open-source projects or research prototypes reviewed documents, in one vendor-neutral and self-hostable component, all five of the following: (1) declarative per-tool and per-parameter policy enforced at the MCP and function-calling boundary; (2) taint labels that follow untrusted tool output to externally visible sinks; (3) an injection detector designed for Arabic as well as English; (4) a ready-to-use human approval channel outside the agent; and (5) a tamper-evident audit trail of every decision. AWS AgentCore Policy covers the first well and the third and fifth partly, but only inside AWS. agentgateway and Invariant cover the first in open source, and Invariant also covers part of the second. CaMeL covers the second most rigorously, but only as a research agent architecture.

**Positioning.** Mirsad's contribution is integration and localisation rather than a new security primitive. It combines techniques that the literature has validated separately: default-deny rules on tools and parameters in the style of Progent, Invariant and Cedar; taint rules adapted from FIDES's trusted-action and permitted-flow policies; spotlighting as an optional extra layer; Arabic-aware normalisation and Arabizi rules that respond to the documented evasion techniques; human approval treated as a logged declassification step; and an HMAC-chained audit log with decision replay. It places them in one open-source gateway that needs no change to the agent, and evaluates the result on Arabic and English scenarios with a method adapted from AgentDojo. Mirsad does not claim to be the only tool-layer firewall, the only system with per-parameter policy or the only Arabic-capable detector, because AgentCore Policy, agentgateway, Invariant, Lakera and Bedrock Guardrails each contradict one of those claims. Its taint tracking is also weaker than CaMeL's, because a proxy cannot see the data flow inside the model.

**Limits.** Several limits follow from this position and from the literature reviewed.

- *Coarse taint causes approval friction.* Session-level taint over-approximates, and label creep turns into approval requests; Section 4.2.4 measures this friction on Mirsad-Bench. Whether approvers can handle it without fatigue has not yet been tested with users.
- *Value matching is incomplete.* An agent that paraphrases, translates or re-encodes data defeats value-level matching, and only the session-level rules then apply.
- *The detector is a signal, not a boundary.* Attackers who can query it will find inputs that evade it, as they have for every detector in Section 2.1.4.
- *Detection accuracy and attack success are not yet measured.* Both depend on attack-labelled data written by the team (Section 3.6.4); Sections 4.2.2 and 4.2.3 report them once that data exists.
- *Scope.* Mirsad mediates tool calls only. Backdoors planted during training, supply-chain compromise of MCP servers, tools that bypass the gateway, and harm that occurs only in text, such as a biased summary, are outside its reach.
- *Audit trust.* The HMAC chain reveals tampering only by parties who do not hold the key, and truncation of the newest events needs an external anchor.
- *A moving landscape.* The products compared change month to month, and several of the open-source projects reviewed have been archived or have lost their hosted services. The comparison reflects the documentation available on 11 October 2026.
