# Chapter 3 – Methodology

This chapter explains how the project was approached, how requirements were obtained, how the system is designed, how it was built and tested, and which ethical, legal and security considerations shaped it.

## 3.1 Research Design / Project Approach

Mirsad is primarily an **implementation project with a quantitative evaluation**, i.e. a design-science approach [@hevner2004design]: an artefact (the gateway) is built to address an identified organisational problem and is then evaluated against criteria fixed in advance. A purely qualitative design would not answer the central question of Section 1.2, which is about measurable reductions in attack success, false positives and latency. A purely experimental study without a working artefact would not satisfy the IS499 learning outcomes, which require designing, implementing and evaluating an information system.

The evaluation is quantitative and comparative:

- **Controlled experiments on Mirsad-Bench.** The same user tasks and attacks are run against an unprotected agent (baseline) and against the agent behind Mirsad, under several configurations (full protection and ablations with single layers enabled). Two agent types are used: a deterministic *worst-case compliant* agent that always obeys any injected instruction that reaches it, which isolates the effect of the gateway from the model's own robustness, and a real LLM agent (Qwen2.5-7B), so far exercised only in a smoke run of {{reports/results_summary.json#bench.llm_smoke.tasks}} tasks.
- **Classifier evaluation.** The injection detector is evaluated with precision, recall, F1, false-positive rate and ROC-AUC on held-out test sets written separately from the training data, plus, once the team adds it, an external public English dataset for out-of-distribution evidence.
- **Performance measurement.** Added latency is measured over HTTP against a direct tool call.
- **Verification.** Automated unit, integration and API tests, security tests of the gateway itself, and audit-replay checks confirm that the functional and non-functional requirements are met.

The success criteria in Section 1.3 were set in the proposal *before* implementation, which protects the evaluation from being tuned to the results.

## 3.2 Data Collection / Requirements Gathering

### 3.2.1 Elicitation methods

Mirsad addresses an emerging threat for which there is no installed user base to observe, so requirements were gathered from several complementary sources rather than from a single existing system:

1. **Document and standards analysis.** The approved proposal (SPAP), the OWASP Top 10 for LLM Applications [@owasp2024llmtop10], the MCP specification [@mcp2026spec], the NCA Essential Cybersecurity Controls [@nca2024ecc], the PDPL [@ksa2021pdpl] and the NIST AI RMF [@nist2023airmf] were analysed for obligations that a control point must satisfy (logging, access control, human oversight, personal-data protection).
2. **Literature and benchmark analysis.** Attack taxonomies and threat models from Greshake et al. [@greshake2023indirect], AgentDojo [@debenedetti2024agentdojo] and InjecAgent [@zhan2024injecagent] were used to derive the attacker goals the gateway must defeat (exfiltration, destructive actions, fraud, phishing, persistence) and the success metrics.
3. **Analysis of existing solutions.** The documentation of commercial and open-source guardrails was reviewed (Section 2.2) to identify missing capabilities, which became the differentiating requirements (action-level policy, taint tracking, Arabic detection, approval, verifiable audit).
4. **Threat modelling.** A STRIDE analysis of the data-flow diagram (Section 3.3.8) produced the security requirements of the gateway itself (authentication, integrity of the audit log, fail-safe approvals, input limits).
5. **Personas and scenarios.** The personas of Section 1.5.1 and end-to-end usage scenarios of the simulated workspace were used to write use cases and to set usability targets such as deciding on an approval in under 30 seconds.
6. **Prototyping and supervisor reviews.** Under the agreed process, requirements are refined iteratively: working increments, starting with the Senior Project I prototype at milestone M3, are demonstrated in the bi-weekly supervisor meetings, and the resulting changes are recorded as backlog items.

**Selection criteria.** Sources were chosen by three criteria. The first was authority over the target setting: the standards and regulations that a Saudi organisation deploying agents must answer to or is likely to adopt (OWASP Top 10 for LLM Applications, NCA ECC, PDPL, NIST AI RMF and the MCP specification itself). The second was relevance to tool-using agents and *indirect* injection rather than chat-only jailbreaks. The third, for benchmarks, was an evaluation method that judges attack success on the side effects of tool calls and reports utility beside security, as AgentDojo and InjecAgent do, so that the method could be adapted to Arabic scenarios.

**Tools.** Research notes and the product comparison were kept as Markdown files under version control (`docs/research/`); the use-case, data-flow and threat-model diagrams were drawn in Mermaid (`docs/diagrams/`); and the requirements, use cases and acceptance criteria were written as tables in the report sources, so that the SRS (D3) and this chapter share one copy.

**Primary stakeholder data.** No interviews have been held and the stakeholder questionnaire in Appendix F has not been administered yet, so the requirements rest on the documentary sources above rather than on practitioner input. The team plans to administer the questionnaire, in particular its Section D, together with the user study described in Section 4.2.8, and to report aggregate results with the number of respondents.


### 3.2.2 Threat model and assumptions

The gateway protects against an **external attacker who can place content in data sources that the agent reads** (send an e-mail, publish or edit a web page, upload a document, write a review or support ticket, or poison a CRM note through a public form), which is the indirect prompt-injection model of [@greshake2023indirect]. The attacker cannot modify the agent's code, its system prompt, the gateway or its configuration, and cannot read the gateway's secrets. The attacker succeeds if the agent performs an action that serves the attacker: sending data to an attacker-controlled destination, deleting or corrupting records, transferring money, sending phishing messages, or planting instructions for later. The LLM itself is treated as *untrusted after it has read untrusted content*: Mirsad does not try to make the model robust, it constrains what the model's tool calls can achieve. Insider attacks on the audit log are considered up to the point of an attacker who does not hold the HMAC key.
