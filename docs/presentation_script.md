## Slide-by-slide script

### Slide 1 – Title and team

**Presenter:** Abdulmalik bin Saedan · **Time:** 0:30

Good morning. We are the Mirsad team: Mohammed Alanssari, Bader Alshuraie, Bader Alyamini, Abdullah Al-Orabi and I, Abdulmalik bin Saedan. Our supervisor is Dr. Omaia Al-Omari. Mirsad is Arabic for "watchtower". It is a runtime security firewall that sits between an AI agent and the tools the agent uses. We will explain the problem, how Mirsad works, how we built and tested it and what we measured, and then show it running.

### Slide 2 – The problem

**Presenter:** Abdulmalik bin Saedan · **Time:** 1:00

AI agents no longer only chat. They read e-mail, search the CRM, open web pages and call tools that send messages or move money. Everything a tool returns goes into the model's context, and the model cannot reliably separate data from instructions. An attacker therefore does not need to break into anything. It is enough to send an e-mail, publish a web page or upload a CV that contains instructions addressed to the agent, for example to export the customer list to an outside address. When the agent reads that content during a normal task, it may follow the instructions with its own valid permissions. This is indirect prompt injection [@greshake2023indirect]. A web application firewall, identity management or data-loss prevention sees an authorised agent making a normal API call, so none of them intervenes. The control has to sit where the agent acts, at the tool call.

### Slide 3 – Why it matters

**Presenter:** Mohammed Yasser Alanssari · **Time:** 0:45

Three facts make this urgent for Saudi organisations. OWASP ranks prompt injection first, as LLM01, in its Top 10 for LLM applications [@owasp2024llmtop10]. Under the Personal Data Protection Law, an agent that leaks customer records causes an unauthorised disclosure of personal data [@ksa2021pdpl], and the NCA Essential Cybersecurity Controls require event logging and monitoring [@nca2024ecc]. Finally, the agents deployed here read and write Arabic, but none of the injection detectors in our review of eleven products and research prototypes has an independent Arabic evaluation, and none covers Gulf dialect or Arabizi.

### Slide 4 – Objectives

**Presenter:** Abdullah Naif Al-Orabi · **Time:** 0:45

The proposal listed six objectives. We consolidated them into three SMART objectives, and the targets were fixed before implementation, so they could not be tuned to the results. First, enforce security at the tool boundary for MCP and OpenAI-style agents, with a median added latency of at most 200 milliseconds per call. Second, detect injected instructions in Arabic and English with an F1 score of at least 0.85 on held-out test sets. Third, keep humans in control through a mobile approval app and a replayable, tamper-evident audit log, and show on our benchmark that attack success falls by at least 80 percent while no more than 5 percent of benign actions are blocked.

### Slide 5 – Related work and gap

**Presenter:** Abdullah Naif Al-Orabi · **Time:** 0:50

We reviewed commercial guardrails, open-source gateways and research prototypes; the table shows five representative systems. Lakera Guard classifies text and lists Arabic, but it returns a verdict and leaves enforcement to the application. AWS AgentCore Policy enforces per-tool and per-parameter rules, but only inside AWS. agentgateway is open and vendor-neutral, but has no data-flow tracking, detector or approval channel. CaMeL gives the strongest guarantees through data-flow tracking, but the agent has to be rebuilt around its interpreter [@debenedetti2025camel]. We do not claim that Mirsad is the only tool-layer firewall. The gap is narrower: none of the systems we reviewed documents all five controls in one vendor-neutral, self-hostable component. Mirsad's Arabic detector is built, but its accuracy is not measured yet; we return to this in the results.

### Slide 6 – Requirements

**Presenter:** Mohammed Yasser Alanssari · **Time:** 0:40

Mirsad addresses a new threat, so there was no installed user base to observe. Requirements came from standards (OWASP, NCA ECC, the PDPL and the NIST AI RMF), the attack literature, the competitor review, a STRIDE threat model, and three personas: a security analyst who approves requests, an AI platform engineer and a compliance officer. The result is 26 functional requirements in eight capability groups and 11 non-functional requirements. Each one has an acceptance criterion that is traced to tests. The targets on the right are the yardsticks we use in the results section.

### Slide 7 – Architecture

**Presenter:** Bader Alshuraie · **Time:** 0:55

Mirsad is one gateway between any agent and its tools. Agents connect through one of three adapters: an MCP proxy, an OpenAI-compatible chat-completions endpoint, or the Guard API with a Python SDK. Adopting Mirsad means pointing the agent at a different address; the agent's code and model stay the same. Inside the gateway there are two paths. The call path runs before a tool executes: policy engine, rate limiter, taint tracker, a deny-overrides decision and, for high-risk calls, a human. The result path runs before the model sees the tool's output: injection detector, sanitising and spotlighting, and taint labelling. Every decision and every inspection is written to the audit log, and the dashboard and approver app use the same REST API.

### Slide 8 – How a tool call is checked

**Presenter:** Bader Alshuraie · **Time:** 0:55

Here is one call in detail. The agent asks to send an e-mail. The policy engine checks that this agent may use the tool and checks each argument against its constraints and rate limits. The taint tracker then asks where the values came from. If the recipient address first appeared inside an untrusted e-mail and never in a trusted field, the attacker chose the destination, so the call is denied. Reasons from all layers are combined, and any deny wins. Allowed calls run, and high-risk calls wait for a human. On the way back, the result is scanned, suspected instructions are removed, untrusted content is marked as data, and its values are recorded for later checks. Each step is written to the audit log.

### Slide 9 – Policy and taint tracking

**Presenter:** Bader Alshuraie, then Bader Abdullah Alyamini · **Time:** 0:55

(Bader Alshuraie) Rules are written in YAML rather than code, so a security team can review them in a pull request. This excerpt comes from the default policy. Sending e-mail is allowed, but a recipient outside najd-trading.example needs approval. Deleting a customer always needs a human, and any tool that is not listed is denied. Constraints cover numeric limits, patterns, lists of allowed domains and rate limits, and administrators can validate, activate and roll back a policy while the gateway runs.

(Bader Abdullah Alyamini) A policy cannot tell where an argument came from. The taint tracker labels every result as trusted or untrusted and as public, internal or confidential, and records the identifying values in it, such as addresses, URLs, IBANs and record IDs. Four rules use that provenance, and the strictest one denies any call whose destination was chosen by untrusted content. The evidence names the source tool, call and field, so the approver can see where the data came from.

### Slide 10 – Detector, approval and audit

**Presenter:** Abdullah Naif Al-Orabi, then Bader Abdullah Alyamini · **Time:** 1:10

(Abdullah Naif Al-Orabi) The detector scans every untrusted result. It first normalises the text: it removes zero-width and direction-control characters, folds look-alike letters and Arabic letter variants, strips diacritics and elongation, and reports these tricks as signals. Weighted rules in English, Arabic (Modern Standard and Gulf) and Arabizi, together with a character n-gram model, then produce a score, and the policy decides whether the result is passed, flagged, sanitised or blocked. We treat the detector as a signal and not as the security boundary, because published adaptive attacks bypass detection-based defences [@zhan2025adaptive]. Policy and taint must stop the action even when the detector misses the text.

(Bader Abdullah Alyamini) When a call needs a human, the approval service writes a short summary in Arabic and English: what the agent wants to do, why Mirsad paused it and where the data came from. It is pushed to the approver's phone. If nobody answers before the timeout, 120 seconds by default, the call is denied. Every event is appended to an HMAC-SHA-256 hash chain, with secrets masked and personal identifiers such as national IDs and IBANs reduced to their last characters. Editing, deleting or reordering an event breaks the chain, and any stored decision can be replayed against the policy version that made it.

### Slide 17 – Conclusion and future work

**Presenter:** Mohammed Yasser Alanssari · **Time:** 0:45

To conclude, we built a working drop-in gateway for MCP and OpenAI-style agents that combines policy, taint tracking, an Arabic and English detector, human approval and a verifiable audit log. On legitimate work it denied no benign call automatically and added about three milliseconds per call. The limits are clear: taint tracking at the proxy is coarser than CaMeL's data-flow tracking, concurrency was measured with one worker and SQLite, and detection accuracy and attack reduction still have to be measured. Next come the team's attack data, detector training and the F1 and attack-success measurements, then a load test with several workers and PostgreSQL, fine-tuning a multilingual encoder, and a pilot with a Saudi organisation.

**Why not just use a prompt-injection classifier?** A classifier gives a probability for a piece of text. When it misses a new phrasing there is no second line, and published adaptive attacks bypass such defences [@zhan2025adaptive]. Mirsad governs the action instead: even if the detector misses, the policy and taint rules still stop the export or the outgoing e-mail.

**How can taint tracking work without seeing inside the model?** It works on values, not on the model's reasoning. Each result's identifying values (addresses, URLs, IBANs, record IDs and word sequences) are recorded with their source. When a later call carries one of those values to an external destination, the rule fires. It is coarser than CaMeL, which tracks data flow inside a custom interpreter, but it needs no change to the agent.

**Why is approval friction {{reports/results_summary.json#bench.scripted_benign_oracle.configs.full.friction|.1%}}? Is that not too high?** All escalations are deliberate in the default policy: every e-mail outside the company domain, every export and every payment or deletion asks a human. Internal replies, lookups, reading and CRM updates had no friction. An organisation that trusts certain partner domains can add them to the policy, and the friction falls accordingly.

**Why are the detector F1 and the attack success rate not reported?** Both need attack-labelled data. The AI assistant used during development does not produce attack text, so the team writes and reviews these examples. The pipeline is ready: `make detector` and the benchmark produce the numbers, and the documents update from the result files. We prefer an honest "pending" to an invented number.

**What happens if the HMAC key is stolen?** Someone holding the key can rewrite the chain consistently, so the log is tamper-evident against anyone without the key, as stated in our threat model. Keeping the key outside the database and exporting the chain head to an external system are the standard mitigations.

**Does Mirsad itself become a target?** Yes, so it is tested as one: agent keys are stored as hashes, users sign in with scrypt-hashed passwords and short-lived tokens with roles, failed logins are throttled and audited, requests are size-limited, policy regular expressions are bounded, and approvals fail safe. These cases are covered by the security test suite.

**Why a progressive web app and not Flutter as in the proposal?** One code base with the dashboard, installation on Android and iOS without store fees or review delays, standard Web Push and offline caching. Wrapping it as a store app remains possible.

**How does this differ from AWS AgentCore Policy?** AgentCore enforces per-tool and per-parameter rules well, but only inside AWS, and it has no provenance labels or approver app. Mirsad is vendor-neutral and self-hosted, adds taint tracking, Arabic detection and an approval channel, and keeps a per-decision, replayable audit record.

**How does Mirsad support the PDPL?** The taint rule for confidential data going to external destinations targets exactly the disclosure the law penalises, identifiers are masked in the audit log, and all demonstration data is fictional.
